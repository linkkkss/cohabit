## 0. 阅读约定

### 0.1 命名与格式

- 枚举值：全大写 `SNAKE_CASE`，存 DB；中文只用于展示。
- JSON key：小写 `snake_case`；`hard_answers`/`soft_answers`/`red_lines`/`tags`/`prompts` 的 key 一旦发布只增不改。
- 时间：DB 存 UTC；API 输出 ISO 8601（`2026-11-15T12:00:00Z`）；前端按浏览器时区展示。
- 分页：`{count,next,previous,results}`；错误：`{code,message,detail}`。
- 空白：所有文本提交先 `strip()`；prompt 内部换行保留，首尾空白去掉；不接受 HTML。
- 长度：字符数按 Unicode code point 计（中文 1 字）；DB 字段长度按 Django `max_length`。

1. 本文件：字段/枚举/题库/公式/JSON schema；

| 枚举 | 值 | 中文 | 说明 |
| --- | --- | --- | --- |

#### 1.3.2 `ContactInfo`

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| `user` | `OneToOne(User)` | `CASCADE` | 1:1 |
| `qq` | `CharField(20)` | 可空 | 5–12 位数字（校验） |
| `wechat` | `CharField(40)` | 可空 | 微信号格式宽松校验 |
| `phone` | `CharField(20)` | 可空 | 中国大陆 11 位手机号（校验） |
| `show_qq` / `show_wechat` / `show_phone` | `Boolean` | 默认 `True/True/False` | 用户级可见开关；最终可见性还要过请求状态 |

**可见规则**（与 02 §1.5 一致）：

- 只在 `GET /api/connections/:id` 且状态 ∈ `{CONTACT_SHARED, CONFIRMING, CONFIRMED}` 时，对请求双方返回；
- 返回前再过 `show_*`；未填/关闭的字段不返回；
- 列表、通知、审计、日志、错误 detail 一律不返回 contact 值；
- 请求过期/关闭后立即隐藏（即使 cron 未跑）。

#### 1.3.3 `Block`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `blocker` | FK User | `CASCADE` | 拉黑者 |
| `blocked` | FK User | `CASCADE` | 被拉黑者 |
| `created_at` | DateTime | 公共 | — |

- `UniqueConstraint(blocker, blocked)`；`CheckConstraint(blocker != blocked)`；
- 双向不可见：匹配候选池、广场、搜索都排除任一方向；
- 拉黑时清理双方在途请求（`close_reason=BLOCKED`），已确认寝室不自动解散（02 X-30）。

### 1.4 `profiles.Profile`

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| `user` | `OneToOne(User)` | `CASCADE` | 1:1 |
| `hard_answers` | `JSONField` | 默认 `{}` | 11 道硬指标；key 见 §3 |
| `soft_answers` | `JSONField` | 默认 `{}` | 6 道软指标 1–5；key 见 §4 |
| `red_lines` | `JSONField` | 默认 `[]` | 0–9 个 red line id；见 §5 |
| `red_lines_confirmed` | `Boolean` | 默认 `False` | 红线步骤已完成（可为“无红线”）；完整度必填 |
| `tags` | `JSONField` | 默认 `[]` | 0–8 个固定标签；见 §6 |
| `prompts` | `JSONField` | 默认 `{}` | 0–3 个 prompt 回答；见 §7 |
| `dims` | `JSONField` | 默认 `{}` | 六维 0–100，**服务端计算** |
| `completeness` | `PositiveSmallInteger` | 默认 0 | 0–100，**服务端计算** |
| `questionnaire_version` | `CharField(10)` | 默认 `"v1"` | 问卷版本；见 §12 |
| `created_at` / `updated_at` | DateTime | 公共 | — |

**约束**：

- `tags` 长度 0–8；元素必须 ∈ 42 个固定标签；不允许重复；
- `red_lines` 长度 0–9；元素必须 ∈ 9 个固定 id；不允许重复；
- `prompts` key 必须 ∈ 6 个固定 key；值 1–120 字；不允许重复 key（JSON 天然唯一）；
- `hard_answers` 只允许 11 个 key；`soft_answers` 只允许 6 个 key；
- `dims`/`completeness` 客户端只读；服务端保存时重算；客户端显式提交时忽略，不报错；
- `questionnaire_version` 服务端设置，只接受 `v1`；客户端提供非 `v1` 返回 `400 QUESTIONNAIRE_VERSION_UNSUPPORTED`（§2.4）。

#### 1.5.2 `RoomMember`

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| `room` | FK Room | `CASCADE` | — |
| `user` | FK User | `CASCADE` | — |
| `role` | `CharField(10)` | `OWNER/MEMBER`，默认 `MEMBER` | 房主唯一 |
| `status` | `CharField(10)` | `ACTIVE/LEFT/REMOVED/ARCHIVED`，默认 `ACTIVE` | 见枚举 |
| `left_at` | DateTime | 可空 | 离开/移除/归档/解散时间 |
| `reason` | `CharField(50)` | 可空，默认 `""` | 见下方取值 |
| `created_at` / `updated_at` | DateTime | 公共 | `created_at` 即加入时间；不另设 `joined_at` |

**枚举**

| 枚举 | 值 | 中文 | 说明 |
| --- | --- | --- | --- |
| `Role` | `OWNER` | 房主 | 每寝同时最多 1 个 ACTIVE OWNER |
| | `MEMBER` | 成员 | — |
| `Status` | `ACTIVE` | 在寝 | 占“一人一 ACTIVE 寝” |
| | `LEFT` | 已退出 | 本人主动退出；不占一人一寝；不可回流 |
| | `REMOVED` | 已移除 | 房主移除；不占；不可回流 |
| | `ARCHIVED` | 已归档 | 窗口结束归档；只读历史；不占一人一寝 |
| `reason` | `VOLUNTARY` | 主动退出 | `LEFT` 时 |
| | `REMOVED_BY_OWNER` | 房主移除 | `REMOVED` 时 |
| | `DISSOLVED` | 寝室解散 | 解散时全员（含房主） |
| | `ARCHIVED` | 窗口归档 | 归档时全员 |
| | `USER_DISABLED` | 用户禁用 | 管理员禁用导致的离开/解散 |

**约束**：

- `UniqueConstraint(user)` where `status=ACTIVE` → `uniq_user_active_room`；
- `UniqueConstraint(room,user)` where `status=ACTIVE` → `uniq_room_active_user`；
- `UniqueConstraint(room)` where `role=OWNER,status=ACTIVE` → `uniq_room_active_owner`；
- 同一 `(room,user)` 允许有多条历史（LEFT/REMOVED/ARCHIVED），但**同一房间不可二次回流**：创建请求时若存在该用户在该房间的任意历史记录 → `409 INVALID_STATE`（`detail.reason=REJOIN_NOT_ALLOWED`）。

> 为什么归档成员不是 `ACTIVE`：ACTIVE 会占“一人一 ACTIVE 寝”，导致归档后无法参加新窗口。见 02 D-01。

**枚举**

| 枚举 | 值 | 中文 | 说明 |
| --- | --- | --- | --- |

| | `APPLY` | 申请入寝 | 申请人→房主 |
| `Status` | `PENDING` | 待对方确认 | 初始 |

| | `CANCELLED` | 已取消 | 发起人/双方撤回 |
| | `EXPIRED` | 已过期 | 超时；close_reason=TIMEOUT |
| `CloseReason` | `DECLINED` | 对方拒绝 | — |
| | `INITIATOR_CANCEL` | 发起人撤回 | PENDING |

### 2.3 写入契约

| 接口 | 行为 |
| --- | --- |
| `PUT /api/me/profile` | 全量替换问卷字段；未提供的字段按空值处理（`hard_answers={}` 等），但 `user` 基本资料不改 |
| `PATCH /api/me/profile` | 局部更新；只更新提供的 key；`red_lines`/`tags`/`prompts` 提供即整体替换 |
| `GET /api/me/profile` | 返回全部字段（含只读 `dims/completeness`） |

- 客户端提交 `dims`/`completeness` 时**忽略并重算**，不报错（避免前端 GET→PUT 耦合）；
- `questionnaire_version` 由服务端写 `v1`；客户端若显式传非 `v1`，返回 `400 QUESTIONNAIRE_VERSION_UNSUPPORTED`；
- 保存顺序：校验 → 归一化 → 计算 `dims` → 计算 `completeness` → 单事务落库；
- 校验失败不落库；返回字段级 `detail.fields`；
- `red_lines` 变更时：若同一请求没有显式 `red_lines_confirmed=true`，服务端把 `red_lines_confirmed` 置 `false`（要求用户重新确认）；仅编辑其他字段不影响已确认状态；
- 硬指标/软指标任何变更都会重算 dims 与 completeness；
- 画像保存不要求完整性；完整度 <100 只影响匹配/组寝门槛，不影响保存。

### 2.4 校验规则

| # | 规则 | 错误码（§10） |
| --- | --- | --- |
| V-01 | `hard_answers` 只能含 11 个 key；缺 key 允许保存但完整度低 | `UNKNOWN_ANSWER_KEY` |
| V-02 | 硬指标 value 必须是对应题目的 option 字符串 | `INVALID_OPTION` |
| V-03 | `soft_answers` 只能含 6 个 key；值必须是整数 1–5（拒绝 bool/字符串） | `INVALID_SOFT_VALUE` |
| V-04 | `red_lines` 只能含 9 个 id；去重；最多 9 个 | `INVALID_RED_LINE` |
| V-05 | `red_lines_confirmed` 必须是 bool | `INVALID_BOOLEAN` |
| V-06 | `tags` 0–8 个；值必须 ∈ 42 个固定标签；去重 | `INVALID_TAG` / `TAG_LIMIT` |
| V-07 | `prompts` 0–3 个；key ∈ 6 个；value 1–120 字 | `INVALID_PROMPT_KEY` / `PROMPT_TOO_LONG` |
| V-08 | `questionnaire_version` 只接受 `v1`（客户端不传则服务端写 v1） | `QUESTIONNAIRE_VERSION_UNSUPPORTED` |
| V-09 | 提交体 ≤ 16KB；单字段不超 DB 长度 | `PAYLOAD_TOO_LARGE` |
| V-10 | 文本去首尾空白；拒绝控制字符（`\x00`–`\x08` 等） | `INVALID_TEXT` |

> 硬指标/软指标缺少不报错（允许分步保存），只是 `completeness` 不到 100。真正的前置门槛在创建请求/进入匹配时由 02 §1.3 抛 `PROFILE_INCOMPLETE`。

### 2.5 服务端计算流水线

```text
normalize(payload)
  → validate_keys/options
  → hard_scores = map_hard_scores(hard_answers)     # 0–100
  → soft_scores = (soft_answers - 1) * 25           # 0/25/50/75/100
  → dims = compute_dims(hard_scores, soft_scores)
  → completeness = compute_completeness(user, payload)
  → save
```

- `dims` 六键必须齐全；缺失的硬指标按“未作答”处理：对应维度只用软指标，完整度不到 100，匹配门槛拦截；
- 不把“未作答”当 0 分参与匹配（避免误伤）；创建请求前已要求完整度 100，所以匹配阶段不会遇到缺项；
- 计算函数是纯函数，输入相同输出相同；不做随机。

### 2.6 完整度公式（精确版）

| 区块 | 分值 | 计算 |
| --- | --- | --- |
| 基本资料 | 20 | `nickname/gender/grade/college/major` 各 4 分；`major` 非空才得分 |
| 硬指标 | 20 | 11 个 key 全部有合法答案得 20；否则 0（全有或全无） |
| 软指标 | 30 | 每个合法答案 5 分；6 个全答得 30 |
| 红线 | 10 | `red_lines_confirmed=true` 得 10；否则 0 |
| 标签 | 10 | `3 <= len(tags) <= 8` 得 10；否则 0 |
| prompts | 10 | `2 <= len(prompts) <= 3` 且每条 1–120 字得 10；否则 0 |
| **合计** | **100** | `completeness` 为整数 0–100 |

- 匹配/创建请求门槛：`completeness == 100`；
- 前端进度环按区块展示（20/20/30/10/10/10），不展示“半分”；
- 修改任意字段后立即重算；管理端可只读查看，不手工改。

### 5.2 语义

- 红线是**用户主动声明**的“不可接受项”，不是系统判定；
- 空数组 + `red_lines_confirmed=true` 表示“没有红线”；
- 空数组 + `red_lines_confirmed=false` 表示“还没确认”，完整度扣 10，匹配门槛拦截；
- 红线不硬性排除候选：列表可见、分数降、详情琥珀色提示、发起请求二次确认（手册 §5.5）；
- 红线冲突计数是**双向独立**：A 的红线命中 B、B 的红线命中 A，各计 1 次；最多 2 次/对（同一 red line 双方都选且都命中则 2 次）。

### 5.3 冲突判定伪代码

```python
def conflicts(a, b):
    out = []
    for rid in a.red_lines:
        if trigger(rid, b.hard_answers):
            out.append({"owner": a.uid, "red_line": rid, "other_value": ...})
    for rid in b.red_lines:
        if trigger(rid, a.hard_answers):
            out.append({"owner": b.uid, "red_line": rid, "other_value": ...})
    return out

def trigger(rid, h):
    if rid == "smoke": return h.get("smoke") in {"sometimes", "yes"}
    if rid == "snore": return h.get("snore") in {"mild", "yes"}
    if rid == "late_return": return h.get("late_return") in {"sometimes", "often"}
    if rid == "pet": return h.get("pet") == "has_pet"
    if rid == "alcohol": return h.get("alcohol") in {"social", "often"}
    if rid == "game_noise": return h.get("game_noise") in {"sometimes", "often"}
    if rid == "visitor_freq": return h.get("visitor_freq") in {"sometimes", "often"}
    if rid == "clean_low": return h.get("clean_freq") in {"weekly", "rarely"}
    # ac_dc 需要双方 ac_temp 分值，单独计算
    raise AssertionError(rid)
```

- `ac_dc` 在 `conflicts()` 里单独处理：`abs(ac_score(a) - ac_score(b)) >= 50`；
- 缺失答案时不触发（不误判）；完整度门槛保证匹配时 11 题齐全。

## 8. 匹配算法 v1

### 8.1 输入与输出

| 项 | 内容 |
| --- | --- |
| 输入 A | 当前用户 `Profile`（dims 六维、tags、red_lines、completeness、questionnaire_version） |
| 输入 B | 候选用户 `Profile`（同上） |
| 输出 | `score` 0–100、`base`、`tag_bonus`、`red_penalty`、`dims` 对比、`reasons` 3 条、`conflicts` |
| 纯函数 | 不查 DB、不写库；API 层负责取数、过滤、分页 |
| 版本 | 同版本优先；跨版本可算但提示 |

### 8.2 候选池（硬过滤）

候选必须同时满足：

1. `User.status=ACTIVE`，`role=STUDENT`；
2. `college == 当前用户 college`；
3. `gender == 当前用户 gender`；
4. `Profile.completeness == 100`；
5. 没有 `ACTIVE` 的 `RoomMember`（自己没寝）；
6. 不是自己；
7. 双向无 `Block`；
8. 未被管理员禁用；
9. 不是当前用户的已确认室友/当前在途请求对方（可选：列表仍展示但标“在沟通中”；v1 建议排除已在途，减少重复）。

排序：

```text
match_score DESC
→ completeness DESC（同分时）
→ last_active/updated_at DESC
→ uid ASC（稳定分页）
```

分页 20/页；`GET /api/match` 不带 target 时用候选池；`GET /api/match/:uid` 单查；`POST /api/match/:uid/score` 返回同一套分数。

### 8.3 六维生成

> 硬指标分值和软指标分值为 0–100；`round_half_up` 四舍五入到整数。

```text
soft(v) = (v - 1) * 25

sleep_hard = avg(sleep_time, wake_time, late_return)
sleep      = round_half_up(0.7 * soft(sleep_regular) + 0.3 * sleep_hard)

clean      = round_half_up(0.7 * soft(clean) + 0.3 * clean_freq)

social     = soft(social)

noise      = round_half_up(0.7 * soft(noise) + 0.3 * avg(snore, game_noise))

boundary   = round_half_up(0.7 * soft(boundary) + 0.3 * avg(smoke, pet, visitor_freq))

spend      = soft(spend)
```

**口径说明**：

- `alcohol`、`ac_temp` 只用于红线与展示，不进入六维（手册 §5.1：`social`/`spend` 仅软指标）；
- `pet` 分值方向是“接受度”，`no_pet=0/ok=50/has_pet=100`；两人都 `no_pet` 时边界分都低但差异 0，仍可匹配；
- `smoke` 分值方向是“无烟=100”；两人都吸烟时差异 0，红线由各自声明决定；
- 缺失硬指标时，该维度只用软指标（权重全部给软指标），completeness 不到 100，匹配门槛拦截；正常匹配不会遇到；
- dims 落库后不随展示变化；公式变更需升 `questionnaire_version` 并重算（§12）。

### 8.4 契合度公式

```text
dim_score(a,b)[d] = 100 - |a.dims[d] - b.dims[d]|          # 0–100
base = Σ(weight[d] * dim_score[d]) / 100                    # 0–100，权重和=100
tag_bonus = min(6, 2 * |a.tags ∩ b.tags|)                   # 0–6
red_conflict_count = 双向红线命中数                          # 0–2
red_penalty = min(30, 15 * red_conflict_count)              # 0–30
raw = base + tag_bonus - red_penalty
score = clamp(round_half_up(raw), 0, 100)
if red_conflict_count > 0:
    score = min(score, 59)                                 # 红线冲突封顶
```

权重：

| 维度 | `sleep` | `clean` | `social` | `noise` | `boundary` | `spend` |
| --- | --- | --- | --- | --- | --- | --- |
| 权重 | 20 | 20 | 15 | 15 | 15 | 15 |

- `tag_bonus` 只按共同标签数，最多 6；不因标签冲突扣分；
- `red_penalty` 每条 15，最多 30；冲突封顶 59（即使 base 很高）；
- `score` 整数；`base` 返回 1 位小数便于调试；`tag_bonus/red_penalty` 整数；
- 冲突不排除候选；列表仍展示，详情琥珀提示，发起请求二次确认。

### 8.5 推荐理由（3 条）

1. 取 `weight[d] * dim_score[d]` 最大的 2 个维度（同分按维度顺序 `sleep,clean,social,noise,boundary,spend`）；
2. 第 3 条：优先取第一个共同标签（按 `TAG_ORDER`）；没有共同标签则取第 3 个维度；
3. 每条理由 ≤ 60 字；冲突不占理由条数，单独放 `conflicts`。

**模板**

| 维度 | 理由模板 |
| --- | --- |
| `sleep` | 你们的作息节奏很接近，早睡/早起冲突会少很多。 |
| `clean` | 整洁习惯高度一致，公共区摩擦会少很多。 |
| `social` | 社交热度接近，既能一起热闹也能各自安静。 |
| `noise` | 对声音的敏感度接近，耳机/外放分歧小。 |
| `boundary` | 边界感接近，访客和借东西的预期一致。 |
| `spend` | 公共开销分摊习惯接近，费用好商量。 |
| 标签 | 都有「{tag}」标签，容易聊到一起。 |

- 若最高贡献维度差异很大（`dim_score < 50`），不选它做理由，顺延下一个；避免“哪壶不开提哪壶”；
- 理由不足 3 条时，用剩余维度补齐；仍不足则用通用句“你们的画像整体比较接近。”；
- 红线冲突提示不写在 `reasons`，前端从 `conflicts` 单独渲染。

### 8.7 边界与异常

| 场景 | 行为 |
| --- | --- |
| 自己看自己 | `400 INVALID_TARGET`（不计算） |
| 对方不在候选池（学院/性别不同） | `404 PROFILE_NOT_FOUND`（不泄露是否存在） |
| 对方画像不完整 | 不出现在列表；单查返回 `409 PROFILE_INCOMPLETE`（detail.completeness） |
| 双向拉黑 | 不出现在列表；单查 404 |
| 对方已有 ACTIVE 寝 | 不出现在列表；单查 409 `TARGET_IN_ROOM` |
| 版本不同 | 仍可算；`version_warning="对方问卷版本 v1.1，分数仅供参考"`；排序同版本优先 |
| dims 缺失/非法 | 不计算；`409 PROFILE_INCOMPLETE`，不返回 0 分 |
| 分数相同 | 按 completeness→last_active→uid 排序，保证分页稳定 |
| 请求计算别人的分 | 只能算候选池内用户；不能批量导出全站画像 |

### 8.8 性能

- 候选池查询走 `User(college,gender,status)` + `Profile.completeness=100` + `NOT EXISTS RoomMember ACTIVE`；
- 先分页取 200 个候选，再在内存算分排序取 20；避免全表算分；
- 红线冲突/标签交集都是小数组，O(1)；
- `POST /api/match/:uid/score` 单次查询 A/B 两个 Profile；
- 不上缓存（v1 数据量小）；后续可缓存 dims。

## 9. 通知字典

### 9.1 通用规则

- 与业务同事务写入；失败回滚业务；
- `title` ≤ 60 字；昵称/编号超长截断；
- `payload` 只放 id/枚举/人数/时间/原因；**禁止联系方式、邮箱、真名、token、密码**；
- 列表接口返回 `{count,next,previous,results}`；未读角标用未读数接口；
- 已读 90 天、未读 180 天清理；点击跳转后标记已读；
- 同一事件不重复发给同一用户；批量操作每人一条，不合并。

### 9.2 类型与 payload

| `TRANSFER_EXPIRED` | 双方 | `房主转让已过期` | `transfer_id` | `/app/rooms/{code}` |
| `TRANSFER_CANCELLED` | 双方 | `房主转让已取消` | `transfer_id` | `/app/rooms/{code}` |

### 9.3 `SYSTEM` 原因映射

| `reason` | 标题 |
| --- | --- |
| `INITIATOR_CANCEL` | 对方已撤回请求 |
| `END_UNDERSTANDING` | 对方已结束了解 |
| `TIMEOUT` | 请求已过期 |
| `FULL` | 房间已满，请求已关闭 |
| `LOCKED` | 房间已锁定，请求已关闭 |
| `ROOM_DISSOLVED` | 房间已解散 |
| `ARCHIVED` | 组寝窗口已结束 |
| `USER_DISABLED` | 对方账号已被禁用 |
| `RATE_LIMITED` | 请求过于频繁 |
| `ADMIN` | 请求已被管理员关闭 |
| `BLOCKED` | 请求已关闭 |
| `AUTO_CANCELLED` | 你已加入其他寝室 |

> `DECLINED` 是独立类型，不走 `SYSTEM`；`CONFIRMED` 的 `close_reason` 为空，不产生关闭通知。

### 9.4 payload 禁止项

- 不出现 `qq/wechat/phone/email` 值；
- 不出现真实姓名（平台只存昵称）；
- 不出现 JWT/refresh token/session id；
- `room_code` 可放（公开页可查）；`connection_id/transfer_id` 可放（需登录鉴权）；
- `reason` 只放枚举；不放管理员备注/举报内容；
- 通知标题中的昵称使用 `nickname`，不拼接 UID。

## 10. 校验错误 detail 约定

### 10.1 统一格式

```json
{
  "code": "INVALID_OPTION",
  "message": "画像提交有误，请检查后重试。",
  "detail": {
    "fields": {
      "hard_answers.smoke": {
        "code": "INVALID_OPTION",
        "message": "不支持的选项。",
        "allowed": ["no", "sometimes", "yes"]
      }
    }
  }
}
```

- `message` 面向用户，中文，不暴露内部堆栈；
- `detail.fields` 以点路径为 key，支持一次返回多个字段错误；
- 单字段错误也放在 `fields` 里，保持结构一致；
- 业务状态错误用 02 §10.2 的 code；本文件只管画像/匹配校验。

### 10.2 错误码表

| HTTP | code | 触发 | detail |
| --- | --- | --- | --- |
| 400 | `UNKNOWN_ANSWER_KEY` | hard/soft 出现未知 key | `fields.{field}.key` |
| 400 | `INVALID_OPTION` | 硬指标 value 不在选项 | `fields.{field}.allowed` |
| 400 | `INVALID_SOFT_VALUE` | 软指标不是 1–5 整数 | `fields.{field}.min/max` |
| 400 | `INVALID_RED_LINE` | 红线 id 未知/重复 | `fields.red_lines.allowed` |
| 400 | `INVALID_BOOLEAN` | 确认字段不是 bool | `fields.red_lines_confirmed` |
| 400 | `INVALID_TAG` | 标签不在词库/重复 | `fields.tags.allowed` |
| 400 | `TAG_LIMIT` | 标签 >8 | `fields.tags.max` |
| 400 | `INVALID_PROMPT_KEY` | prompt key 未知 | `fields.prompts.allowed` |
| 400 | `PROMPT_TOO_LONG` | prompt >120 字 | `fields.prompts.{key}.max` |
| 400 | `QUESTIONNAIRE_VERSION_UNSUPPORTED` | 版本非 v1 | `fields.questionnaire_version.allowed` |
| 400 | `INVALID_TEXT` | 文本含控制字符 | `fields.{field}` |
| 413 | `PAYLOAD_TOO_LARGE` | 提交体 >16KB | `detail.max_bytes` |
| 409 | `PROFILE_INCOMPLETE` | 匹配/创建请求时完整度 <100 | `completeness`, `missing` |
| 404 | `PROFILE_NOT_FOUND` | 目标不在候选池/不存在 | 不返回目标存在性 |
| 409 | `TARGET_IN_ROOM` | 目标已有 ACTIVE 寝室 | `target_uid` |
| 400 | `INVALID_TARGET` | 目标结构错误（自己/非房主/非成员） | `reason` |

### 10.3 `PROFILE_INCOMPLETE` 示例

```json
{
  "code": "PROFILE_INCOMPLETE",
  "message": "请先完成画像，才能开始匹配。",
  "detail": {
    "completeness": 90,
    "missing": ["soft.sleep_regular", "tags", "prompts"]
  }
}
```

- `missing` 是点路径数组，最多 10 条；前端可跳转到对应步骤；
- 不返回其他用户的完整度/答案；
- 创建请求时由 02 §1.3 抛同一 code。

### 10.4 字段级错误合并

- 一次请求最多返回 20 个字段错误，超出截断并在 `detail.truncated=true`；
- 同类错误只给一条（如多个未知 key，`fields` 逐个列出）；
- 不因一个字段错误丢弃其他字段校验结果（尽量一次给全）。

## 11. Seed 数据规格（`seed_demo --reset`）

### 11.1 原则

- 只用于开发/演示；`DEBUG=False` 时拒绝执行，除非显式 `--force`；
- 不写真实个人信息；昵称/联系方式全部虚构；
- 数据必须满足 02 的所有不变量与唯一约束；
- 计算 dims/completeness 走与生产相同的纯函数，不硬编码不一致的值；
- 固定数据，不用随机；重复执行 `--reset` 得到同一结果（时间相对 `now`）。

### 11.2 账号

| 项 | 值 |
| --- | --- |
| 学院 | `计算机学院`、`外国语学院` |
| 学生 | 每学院 20 人（10 男 10 女），共 40 人 |
| 昵称 | `小算01`…`小算20`、`小外01`…`小外20` |
| 邮箱 | `demo001@stu.edu.cn`…`demo020@stu.edu.cn`（计算机）、`demo021@stu.edu.cn`…`demo040@stu.edu.cn`（外国语） |
| 密码 | `Demo1234!`（开发专用；文档可见） |
| 管理员 | `admin@cohabit.local` / `Admin1234!`，`role=ADMIN`，`is_staff=True` |
| UID | 固定 10 位数字（如 `0000000001`…`0000000040`）；生成规则仍为随机 10 位数字，seed 固定以保证可重复 |
| 年级 | 1–4 分布；至少各年级 5 人 |
| 专业 | 计算机学院：软件工程/计算机科学；外国语学院：英语/日语 |

### 11.3 画像

| 类型 | 数量 | 说明 |
| --- | --- | --- |
| 完整画像 | 40 人全部 | completeness=100；dims 六维；3–6 个标签；0–3 条红线；2–3 条 prompt |
| 红线样本 | 至少 6 人 | 覆盖 smoke/snore/late_return/pet/alcohol/game_noise/visitor_freq/ac_dc/clean_low |

| 标签样本 | 至少 10 人 | 覆盖 6 个分类；至少 3 对用户有共同标签 |

> 空态/引导测试用**新注册且未填画像**的账号，不写入 seed；seed 学生全部完整，保证匹配页/寝室页有数据。

### 11.4 寝室

共 6 间，两个学院各 3 间，覆盖 2/4/6 容量与全部状态：

| # | 学院 | 容量 | 状态 | 成员 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 1 | 计算机学院 | 4 | RECRUITING | 2/4 | 招募中，缺 2；owner 男 |
| 2 | 外国语学院 | 6 | RECRUITING | 3/6 | 招募中，缺 3；owner 女 |
| 3 | 计算机学院 | 4 | FULL | 4/4 | 满员；owner 男 |
| 4 | 外国语学院 | 4 | LOCKED | 3/4 | 锁定但未满；owner 女 |
| 5 | 计算机学院 | 6 | ARCHIVED | 6/6 | 上一窗口归档；成员 ARCHIVED |
| 6 | 外国语学院 | 2 | DISSOLVED | 2/2 | 已解散；成员 LEFT，reason=DISSOLVED |

- 非归档/解散房间每间有 1 个 ACTIVE OWNER；归档/解散保留历史房主记录（`ARCHIVED`/`LEFT`），不参与一人一寝；
- 非终态 `member_count` 与 ACTIVE 成员数一致；归档/解散保留关闭前计数（如 6/6、2/2）；
- 成员同学院同性别；归档/解散房间不参与广场，成员关系保留只读；
- 寝室 code 固定 9 位：`100000001`…`100000006`；避免与真实数据冲突。

### 11.5 请求/转让/通知

| 数据 | 数量 | 覆盖状态 |
| --- | --- | --- |
| `ConnectionRequest` | 共 8 条（两学院各 4 条） | PENDING(2)、CONTACT_SHARED(2)、CONFIRMING(2)、CONFIRMED(2) |
| `RoomTransfer` | 2 条 | PENDING(1)、EXPIRED(1) |
| `Notification` | 每用户 0–5 条 | 未读/已读混合；覆盖 10+ 类型 |
| `TimeWindow` | 每学院 1 条 | 开始=昨天 00:00，结束=+7 天 23:59 |
| `InviteCode` | 1 条 | `COHAB2026`，`max_uses=0`（无限次，开发期） |
| `Report` | 2 条 | OPEN(1)、RESOLVED(1) |
| `Block` | 2 对 | 双向不可见测试 |

- 请求的 `expires_at` 相对 now：PENDING +48h；CONTACT_SHARED +7d；CONFIRMING +48h；已终态按关闭时间；
- 不创建“同一人两个 ACTIVE 寝”“同一对两个 open 请求”等违规数据；
- CONFIRMED 请求对应的寝室/成员必须存在且一致；

### 11.6 命令行为


3. 创建学院/用户/画像/寝室/成员/请求/通知/窗口/邀请码/举报/拉黑；
4. 用 `recompute_profile` 计算 dims/completeness；
5. 输出计数摘要；失败回滚（单事务或分步补偿）。

- 不做“随机 seed”；重复执行结果稳定；
- 不修改已有非 seed 数据；
- 生产环境禁止执行。

## 12. 版本与迁移

### 12.1 版本语义

| 变更 | 版本 | 兼容性 |
| --- | --- | --- |
| 加题/加标签/加红线/prompt（旧字段不变） | `v1.1`（minor） | 旧画像仍可算；新字段缺失则完整度下降 |
| 改选项/改分值/改权重/改维度映射 | `v2`（major） | 旧 dims 失效；需重算/重答 |
| 改文案/改展示顺序 | 不改版本 | 纯展示 |
| 删除题/标签/红线 | 禁止 | 只废弃，不删除 |

- `questionnaire_version` 存 `v1`/`v1.1`/`v2`；`max_length=10` 够用；
- 同版本匹配正常；跨版本可算但 `version_warning`；排序同版本优先；
- 任何公式/权重变更必须重算全部 `dims` 并写审计，不能只改代码。

### 12.2 变更流程

1. 改本文件（题库/公式/枚举）+ 手册 §5；
2. 写决策记录（日期/原因/影响）；
3. 升版本号（minor/major）；
4. 写数据迁移：给旧画像补默认值/重算 dims/completeness；
5. 更新 seed；
6. 回归 02 §13 与 03 §8 用例；
7. 前端同步文案/选项；
8. 发布后监控 `PROFILE_INCOMPLETE`/匹配异常。

### 12.3 兼容策略

| 旧数据 | 处理 |
| --- | --- |
| 缺新硬指标 key | 保存允许；dims 只用软指标；completeness 下降；匹配门槛拦截，引导补答 |
| 缺新软指标 | 同上，按缺失项扣 5 分 |
| 旧标签被废弃 | 保留展示别名；匹配不计入新词库；引导替换 |
| 旧红线 id 废弃 | 保留只读；不再触发；引导移除 |
| prompt key 废弃 | 保留展示；不再计入 completeness；引导重答 |
| `questionnaire_version` 为空 | 迁移置 `v1`；dims 重算 |

### 12.4 重算命令

```text
python manage.py recompute_profiles --version v1 --dry-run
python manage.py recompute_profiles --version v1 --batch 200
```

- 只重算 `dims/completeness`，不改用户答案；
- 输出变更数量/失败数量；写审计 `PROFILE_RECOMPUTED`（actor 为空，meta 含 version/batch）；
- 幂等；可断点续跑（按 id 游标）。
