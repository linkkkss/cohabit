## 0. 范围、术语与约定

### 0.1 覆盖范围

本文件完整定义以下 5 个聚合的状态、动作、守卫、副作用与并发规则：

| 聚合 | 模型 | 职责 |
| --- | --- | --- |
| 组寝请求 | `ConnectionRequest` | 人-人邀请、房主定向邀请、申请入寝；两步确认 |
| 寝室 | `Room` | 容量 2/4/6、招募/满员/锁定/归档/解散 |
| 寝室成员 | `RoomMember` | 一人一寝、房主唯一、退出/移除/归档 |
| 房主转让 | `RoomTransfer` | 24h 内有效、房主与成员角色交换 |
| 时间窗 | `TimeWindow` | 按学院开窗；未配置=关闭；结束归档 |

**不覆盖**：问卷题目/维度算法（见 `docs/03-数据字典与问卷.md`）、匹配排序细节、页面交互、管理员 CRUD 表单（除状态相关动作）、通知文案最终润色。

### 0.2 术语

| 术语 | 定义 |
| --- | --- |
| 发起人 / initiator | 创建请求的一方（邀请人或申请人） |
| 目标 / target | 被邀请人或被申请的房主 |
| 在途 / open | `ConnectionRequest.status ∈ {PENDING, CONTACT_SHARED, CONFIRMING}` |
| 终态 / terminal | `CONFIRMED`、`DECLINED`、`CANCELLED`、`EXPIRED` |
| 活跃成员 / ACTIVE | `RoomMember.status=ACTIVE`，占用“一人一寝”名额 |
| 历史成员 / ARCHIVED | 寝室归档后的成员关系，只读，不占用一人一寝 |
| 窗口开放 | 存在该学院的 `TimeWindow`，且 `start_at <= now < end_at` |
| 写操作 | 会修改业务状态的请求；学生端写操作全部受时间窗约束（Admin 运维动作例外，见 §1.4） |
| 懒过期 | 写操作发现 `expires_at <= now` 时，先在同一事务内将请求置为 `EXPIRED`，再返回 409 |

### 0.3 时间与存储

- 数据库统一存 UTC；API 返回 ISO 8601（`2026-11-15T12:00:00Z`）；前端按 `Asia/Shanghai` 展示。
- 过期判断只用服务端时间；不信任客户端时间。
- `expires_at` 在每次状态迁移时重算，不允许为空（在途请求必须有到期时间）。
- 所有“现在”以 `django.utils.timezone.now()` 为准；测试可用 `freezegun` 或注入 clock。

### 0.4 动作与状态迁移原则

1. 状态只能通过本文件列出的 service 动作迁移；View/Serializer/Admin 不直接改 `status` 字段。
2. 终态不可回到在途状态；唯一例外是数据库运维修复，必须走 `docs/决策记录.md` 并审计。
3. 同一动作重复提交：若已是目标状态 → `409 ALREADY_CONFIRMED`（确认）或 `409 INVALID_STATE`（其他）；不返回成功，避免前端误判。
4. 任何失败都整体回滚：不写半成品、不发通知、不写“成功”审计。
5. 通知与审计在业务事务内落库（`Notification`/`AuditLog` 行），外部投递（邮件/推送）本期无；站内轮询读取。
6. 联系人信息不得进入 `Notification.payload`、`AuditLog.meta`、日志、错误详情；只允许在 `GET /api/connections/:id` 的 `contact` 字段按状态返回。

### 0.5 参与者与权限速查

| 动作 | 谁可以 | 状态要求 |
| --- | --- | --- |
| 创建 INVITE | 学生（画像完整、无寝室、同院同性别、未拉黑） | 窗口开放 |
| 创建 APPLY | 学生（画像完整、无寝室、同院同性别、未拉黑） | 窗口开放 |
| accept | 目标 | `PENDING` |
| decline | 目标 | `PENDING` |
| cancel（撤回） | 发起人 | `PENDING` |
| cancel（结束了解） | 任一方 | `CONTACT_SHARED` / `CONFIRMING` |
| confirm | 双方各自 | `CONTACT_SHARED` → 第一步；`CONFIRMING` → 第二步 |
| 锁定/解锁 | 房主 | `RECRUITING` → `LOCKED`；`LOCKED` → `RECRUITING` |
| 退出 | 非房主成员 | `ACTIVE` |
| 移除 | 房主 | 目标是 `ACTIVE` 非房主成员 |
| 解散 | 房主 | 非终态寝室 |
| 转让发起/取消 | 房主 | 非终态寝室、无其他 pending 转让 |
| 转让接受/拒绝 | 目标成员 | `PENDING` 且未过期 |
| 管理员关闭请求/强制解散 | Admin | 任意在途/非终态；写审计 |

## 1. 全局守卫与执行顺序

所有学生端**组寝写操作**按以下顺序执行；前一步失败不再继续。顺序写进 service 基类/装饰器，避免各动作实现不一致。资料/问卷/举报/通知已读不走此链。

### 1.1 守卫链

```text
1. 认证：JWT 有效；用户存在且 status=ACTIVE；否则 401 / 403 ACCOUNT_DISABLED
2. 角色：学生端动作只允许 role=STUDENT；Admin 走 Admin/运维动作
3. 时间窗：window_open(user.college) == True；否则 409 WINDOW_CLOSED
4. 画像：user.profile.completeness == 100；否则 409 PROFILE_INCOMPLETE
   （仅创建/接受/确认需要；查询不需要）
5. 参与者：请求存在且 user ∈ {initiator, target}；否则 404 / 403 NOT_PARTICIPANT
6. 状态：动作允许的当前状态；否则 409 INVALID_STATE
7. 业务守卫：性别/学院/寝室状态/容量/拉黑/重复/限频（按动作）
8. 事务与锁：按 §11 的顺序加锁，重读状态并再次校验
9. 写业务字段 + 通知 + 审计
10. 提交；返回新状态
```

### 1.2 404 与 403 的边界

- 请求不存在、或当前用户既不是发起人也不是目标 → `404 CONNECTION_NOT_FOUND`（不泄露“存在但无权”）。
- 请求存在且用户是参与者，但动作不属于其角色（如目标撤回 PENDING、发起人接受） → `403 FORBIDDEN`。
- 寝室不存在/已解散且非成员 → `404 ROOM_NOT_FOUND`；存在但无权写 → `403 NOT_OWNER` / `403 NOT_MEMBER`。

### 1.3 懒过期

对于 `PENDING` / `CONTACT_SHARED` / `CONFIRMING` 的请求，任何写动作（accept/decline/cancel/confirm）在加锁后先检查：

```python
if req.expires_at <= now:
    close_connection(req, status=EXPIRED, close_reason=TIMEOUT)
    notify_both(req, "SYSTEM", {"connection_id": ..., "reason": "TIMEOUT"})
    audit(req, "CONNECTION_EXPIRED")
    raise Conflict("REQUEST_EXPIRED")
```

- 这样即使 cron 延迟，也不会出现“过期还能接受”的窗口。
- cron 仍按 §3.6 周期运行；懒过期与 cron 都幂等。

### 1.4 时间窗对 Admin 的例外

- 学生端：窗口关闭后所有**组寝写操作**禁止（含创建/accept/decline/cancel/confirm/锁定/退出/移除/解散/转让）；只读可用。注册/登录、资料与问卷编辑、举报、拉黑、通知已读不受影响。
- Admin 的运维动作（关闭请求、强制解散、禁用用户、归档修复）**不受时间窗限制**，但必须写审计；不得以 Admin 身份代替用户 confirm/accept。
- cron 在窗口关闭后运行，不受窗口限制。

### 1.5 性别与学院

- 注册时写入 `User.gender`；学生不可自改（`403 GENDER_IMMUTABLE`）；Admin 可改并审计。
- `Room.gender` 在创建时快照为发起人性别；之后不随成员/用户改变。
- 请求创建、accept、confirm 都重新校验：
  - `initiator.gender == target.gender`
  - 对寝室请求：`target.gender == room.gender`（APPLY 的 target 是房主，房主性别=room.gender）
  - `initiator.college == target.college == room.college`
- 管理员改了用户性别/学院导致不一致时：请求在下次写操作返回 `403 WRONG_GENDER` / `403 WRONG_COLLEGE`；不自动改历史寝室。

## 2. 状态总览

### 2.1 ConnectionRequest

```text
                         accept                 confirm(第一方)
PENDING ────────────────────────▶ CONTACT_SHARED ─────────────────▶ CONFIRMING
  │                                    │                               │
  │ decline                            │ cancel                        │ confirm(第二方)
  │ cancel(发起人)                     │                               ▼
  │ expire                             │ expire                    CONFIRMED
  ▼                                    ▼
DECLINED / CANCELLED / EXPIRED     CANCELLED / EXPIRED
```

- `PENDING`：已发出，等待目标接受/拒绝；发起人可撤回。
- `CONTACT_SHARED`：目标已接受，联系方式对双方可见；尚未有人确认。
- `CONFIRMING`：一方已确认，等待另一方；联系方式仍可见。
- `CONFIRMED`：双方确认，寝室已建立/入寝完成；终态成功。
- `DECLINED` / `CANCELLED` / `EXPIRED`：终态失败；联系方式隐藏。

### 2.2 Room

```text
                 join(confirm) / 成员退出/移除
RECRUITING ◀──────────────────────────────────▶ FULL
    │  ▲                                          │
    │  │ unlock                                   │ 成员退出/移除
    ▼  │                                          ▼
  LOCKED                                      RECRUITING
    │
    ├── dissolve ──▶ DISSOLVED
    └── archive  ──▶ ARCHIVED
RECRUITING / FULL / LOCKED ── dissolve/admin ──▶ DISSOLVED
RECRUITING / FULL / LOCKED ── window end  ──▶ ARCHIVED
```

- `RECRUITING`：有空位，可被申请/邀请，出现在广场。
- `FULL`：满员；不可再加入；可退出/移除/转让/解散。
- `LOCKED`：房主暂停招募；不可加入；可退出/移除/转让/解散/解锁；不参与广场。
- `ARCHIVED`：窗口结束的只读历史；成员关系转 `ARCHIVED`；不可写。
- `DISSOLVED`：房主/管理员解散；成员转 `LEFT`；不可写。

### 2.3 RoomMember

```text
ACTIVE ── leave ──────▶ LEFT
ACTIVE ── remove ─────▶ REMOVED
ACTIVE ── dissolve ───▶ LEFT (reason=DISSOLVED)
ACTIVE ── user disable ▶ LEFT (reason=USER_DISABLED)
ACTIVE ── archive ────▶ ARCHIVED
LEFT / REMOVED / ARCHIVED ──▶ 不可回流
```

### 2.4 RoomTransfer

```text
PENDING ── accept ──▶ ACCEPTED（角色交换）
PENDING ── decline ─▶ DECLINED
PENDING ── cancel ──▶ CANCELLED
PENDING ── 24h ─────▶ EXPIRED
PENDING ── 房间解散/归档/目标离开 ──▶ CANCELLED
```

## 3. ConnectionRequest（组寝请求）

### 3.1 字段语义

| 字段 | 类型 | 语义 / 规则 |
| --- | --- | --- |
| `id` | UUID | 主键；API 路径使用 |
| `type` | enum | `INVITE` / `APPLY` |
| `initiator` | FK User | 发起人 |
| `target` | FK User | 目标（被邀请人 / 被申请房主） |
| `room` | FK Room, null | APPLY 必填；INVITE 可空（人-人邀请）或自有寝室（房主定向邀请） |
| `capacity_pref` | int, null | 仅 `INVITE` 且 `room=null` 时=2/4/6；其他为空 |
| `status` | enum | 见 §2.1 |
| `close_reason` | enum/空 | 终态原因，见 §3.7 |
| `contact_shared_at` | datetime, null | 目标 accept 的时刻；联系方式开始可见 |
| `initiator_confirm_at` | datetime, null | 发起人确认时刻 |
| `target_confirm_at` | datetime, null | 目标确认时刻 |
| `expires_at` | datetime | 在途到期；随迁移重算 |
| `created_at` / `updated_at` | datetime | 审计字段 |
| `version` | int | 乐观锁预留；正确性以行锁为准，不依赖 version |

**约束**：

- `type=APPLY ⇒ room IS NOT NULL`。
- `type=INVITE AND room IS NULL ⇒ capacity_pref ∈ {2,4,6}`。
- `type=INVITE AND room IS NOT NULL ⇒ capacity_pref IS NULL`。
- `type=APPLY ⇒ capacity_pref IS NULL`。
- `initiator_id != target_id`。
- 终态时 `close_reason` 非空（`CONFIRMED` 除外，允许为空）。

**在途唯一性**（服务层 + 数据库部分唯一索引）：

| 场景 | 约束 | 索引名建议 |
| --- | --- | --- |
| 同一对用户同方向 | 在途 `(initiator, target)` 唯一 | `uniq_open_pair_direction` |
| 同一寝室对同一目标 | 在途 `(room, target)`（`type=INVITE`）唯一 | `uniq_open_room_invite` |
| 同一寝室对同一申请人 | 在途 `(room, initiator)`（`type=APPLY`）唯一 | `uniq_open_apply` |

> **反向重复**（A→B 与 B→A 同时存在）数据库无法用单列唯一约束表达；由 §3.2 的“锁双方 User 行 + 双向查询”保证。M2 验收必须覆盖并发用例 C-10/C-11。

### 3.2 创建请求

#### 3.2.1 三条入口

| 入口 | type | room | capacity_pref | initiator | target |
| --- | --- | --- | --- | --- | --- |
| 人-人邀请 | `INVITE` | `NULL` | 2/4/6 | 无寝室学生 | 无寝室学生 |
| 房主定向邀请 | `INVITE` | 房主自有寝室 | `NULL` | 房主 | 无寝室学生 |
| 申请入寝 | `APPLY` | 目标房主的寝室 | `NULL` | 无寝室学生 | 房主 |

#### 3.2.2 守卫

**所有入口共同**：

| 守卫 | 失败码 | HTTP |
| --- | --- | --- |
| 当前用户 `status=ACTIVE` | `ACCOUNT_DISABLED` | 403 |
| 窗口开放 | `WINDOW_CLOSED` | 409 |
| 当前用户画像完整度=100 | `PROFILE_INCOMPLETE` | 409 |
| `initiator != target` | `SELF_REQUEST` | 400 |
| 目标存在且 `status=ACTIVE` | `USER_NOT_FOUND` | 404 |
| 双方同学院 | `WRONG_COLLEGE` | 403 |
| 双方同性别 | `WRONG_GENDER` | 403 |
| 双方无拉黑（任一方向） | `BLOCKED` | 403 |
| 双方均无 ACTIVE 寝室 | `ALREADY_IN_ROOM`（自己）/ `TARGET_IN_ROOM`（对方） | 409 |
| 目标画像完整度=100 | `TARGET_PROFILE_INCOMPLETE` | 409 |
| 双方之间无在途请求（任一方向、任意类型） | `DUPLICATE_REQUEST` | 409 |
| 在途请求数（作为 initiator）< 3 | `RATE_LIMITED` | 429 |
| 当日发起数（作为 initiator）< 10 | `RATE_LIMITED` | 429 |
| 未被目标在 24h 内拒绝过（同一对用户） | `COOLDOWN` | 429 |

**房主定向邀请额外**：

- `initiator` 是该寝室 `RoomMember(role=OWNER,status=ACTIVE)`；否则 `403 NOT_OWNER`。
- 寝室 `status=RECRUITING` 且 `member_count < capacity`；否则 `409 ROOM_FULL` / `409 ROOM_LOCKED` / `409 ROOM_ARCHIVED` / `409 ROOM_DISSOLVED`。
- 目标不是该寝室 ACTIVE 成员。

**申请入寝额外**：

- `target` 是该寝室 ACTIVE 房主；否则 `403 NOT_OWNER`（不泄露寝室归属时用 404）。
- 寝室状态/空位同上。
- 申请人不是该寝室成员。

**人-人邀请额外**：

- `capacity_pref ∈ {2,4,6}`；否则 `400 CAPACITY_INVALID`。
- 双方均无 ACTIVE 寝室（共同守卫已覆盖）。

#### 3.2.3 事务与锁

```python
with transaction.atomic():
    # 1) 锁双方 User 行，按 id 升序；防止 A→B 与 B→A 并发穿透
    users = list(User.objects.select_for_update().filter(id__in=[me.id, target.id]).order_by("id"))
    # 2) 重读状态/寝室/拉黑/在途（反向也查）
    # 3) 限频计数（作为 initiator 的 open 数、当日创建数）
    # 4) 校验画像/学院/性别/窗口
    # 5) 创建 ConnectionRequest
    req = ConnectionRequest.objects.create(
        type=..., initiator=me, target=target, room=room,
        capacity_pref=capacity_pref, status=PENDING,
        expires_at=now + timedelta(hours=48),
    )
    # 6) Notification(target, CONNECTION_RECEIVED) + AuditLog(CONNECTION_CREATED)
```

- **锁 User 行是创建的关键**：同一个人同时发起多条时串行化；A→B / B→A 也串行化。
- 限频计数在锁内做，避免并发创建突破 3 条/10 条。
- 创建后不预留寝室容量；容量只在 confirm 时锁定并校验。

#### 3.2.4 副作用

| 副作用 | 内容 |
| --- | --- |
| 状态 | `PENDING`；`expires_at=now+48h` |
| 通知 | 目标：`CONNECTION_RECEIVED`，payload `{connection_id, type, from_nickname, room_code?}`；不包含联系方式 |
| 审计 | `CONNECTION_CREATED`，meta `{type, room_id?, capacity_pref?}` |
| 限频 | 计入“在途/当日发起” |

#### 3.2.5 幂等与错误

- 重复提交同一目标：第二次命中 `DUPLICATE_REQUEST`（409），不创建第二条。
- 目标在提交瞬间被禁用/拉黑：事务内重读后按对应错误返回。
- 数据库唯一冲突：捕获 `IntegrityError`，转换为 `409 DUPLICATE_REQUEST`，不返回 500。

### 3.3 接受（accept）

| 项 | 规则 |
| --- | --- |
| 操作者 | 目标本人 |
| 当前状态 | `PENDING` |
| 窗口 | 必须开放；关闭 → `409 WINDOW_CLOSED` |
| 懒过期 | `expires_at <= now` → 先关闭为 `EXPIRED/TIMEOUT`，返回 `409 REQUEST_EXPIRED` |
| 重复 accept | `409 INVALID_STATE`（已是 CONTACT_SHARED 或更后） |
| 拉黑 | 任一方向拉黑 → `403 BLOCKED` |
| 寝室 | 双方均无 ACTIVE 寝室；否则 `409 ALREADY_IN_ROOM` / `TARGET_IN_ROOM` |
| 画像 | 双方完整度=100；否则 `409 PROFILE_INCOMPLETE` |
| 性别/学院 | 仍一致；否则 `403 WRONG_GENDER` / `403 WRONG_COLLEGE` |
| 房间（room 非空） | 寝室仍 `RECRUITING`、有空位；否则 `409 ROOM_*` |
| 转让/锁定 | 锁定即 `ROOM_LOCKED`；转让不影响 accept |

**事务**：

```python
with transaction.atomic():
    req = ConnectionRequest.objects.select_for_update().get(pk=req_id)
    assert req.target_id == me.id
    lazy_expire_if_needed(req, now)
    if req.status != PENDING: raise Conflict("INVALID_STATE")
    check_window(me.college)
    check_not_blocked(req)
    check_users_active(req)
    check_profiles_complete(req)
    check_both_no_active_room(req)
    if req.room_id:
        room = Room.objects.select_for_update().get(pk=req.room_id)  # 锁顺序见 §11
        ensure_room_joinable(room)  # 只校验，不占位
    req.status = CONTACT_SHARED
    req.contact_shared_at = now
    req.expires_at = now + timedelta(days=7)
    req.save(update_fields=[...])
    notify(req.initiator, CONTACT_SHARED, {"connection_id": req.id})
    # 目标刚执行 accept，不重复通知自己
    audit(req, CONNECTION_ACCEPTED)
```

**副作用**：

- 状态 `CONTACT_SHARED`，`contact_shared_at=now`，`expires_at=now+7d`。
- 发起人收到 `CONTACT_SHARED` 通知；目标刚执行 accept，不重复通知；`GET /api/connections/:id` 开始返回双方联系方式。
- 不创建寝室、不占位；后续 confirm 仍可能因满员/锁定失败。

**错误语义**：accept 成功只代表“愿意继续了解”，不代表“一定组寝成功”；前端文案必须区分。

### 3.4 拒绝（decline）与取消（cancel）

#### 3.4.1 decline

| 项 | 规则 |
| --- | --- |
| 操作者 | 目标 |
| 当前状态 | `PENDING` |
| 窗口 | 开放；关闭 → `409 WINDOW_CLOSED` |
| 副作用 | `status=DECLINED`、`close_reason=DECLINED`、`expires_at` 保留；通知发起人 `DECLINED`；审计 `CONNECTION_DECLINED` |
| 冷却 | 同一对用户 24h 内不可再次发起（任一方向）；以 `updated_at` 计算 |
| 联系方式 | 从未可见；关闭后仍不可见 |

- 目标不能“取消” PENDING（`403 FORBIDDEN`）；必须显式拒绝，以便发起人收到 `DECLINED` 并进入冷却。
- 拒绝不写寝室、不改成员。

#### 3.4.2 cancel

| 场景 | 操作者 | close_reason | 说明 |
| --- | --- | --- | --- |
| `PENDING` 撤回 | 仅发起人 | `INITIATOR_CANCEL` | 目标不能撤回；目标走 decline |
| `CONTACT_SHARED` 结束了解 | 任一方 | `END_UNDERSTANDING` | 已交换联系方式后仍可退出 |
| `CONFIRMING` 结束了解 | 任一方（含已确认方） | `END_UNDERSTANDING` | 未成立前可退出；提醒前端“对方可能已确认” |

- 状态 → `CANCELLED`；通知另一方 `SYSTEM`，payload `{connection_id, reason}`；审计 `CONNECTION_CANCELLED`。
- 不触发冷却（避免用户不敢退出）。
- 取消后联系方式隐藏；已成立寝室不受影响（CONFIRMED 不可取消）。
- 重复取消/已关闭 → `409 INVALID_STATE`。

### 3.5 确认（confirm）

confirm 是唯一会创建寝室或加入寝室的用户动作，必须最严格。

#### 3.5.1 前置校验

| 检查 | 失败 |
| --- | --- |
| 当前用户是 initiator 或 target | `403 NOT_PARTICIPANT` |
| 状态 ∈ {`CONTACT_SHARED`, `CONFIRMING`} | `409 INVALID_STATE` |
| 本人尚未确认（对应 timestamp 为空） | `409 ALREADY_CONFIRMED` |
| 窗口开放 | `409 WINDOW_CLOSED` |
| 双方账户 ACTIVE | `403 ACCOUNT_DISABLED` |
| 双方画像完整度=100 | `409 PROFILE_INCOMPLETE` |
| 无拉黑 | `403 BLOCKED` |
| 性别/学院一致 | `403 WRONG_GENDER` / `403 WRONG_COLLEGE` |
| 人-人邀请：双方均无 ACTIVE 寝室 | `409 ALREADY_IN_ROOM` / `409 TARGET_IN_ROOM` |
| 寝室邀请/申请：寝室仍 `RECRUITING` 且有空位 | `409 ROOM_FULL` / `ROOM_LOCKED` / `ROOM_ARCHIVED` / `ROOM_DISSOLVED` |
| 寝室邀请/申请：加入方仍无 ACTIVE 寝室 | `409 ALREADY_IN_ROOM` |
| 寝室邀请/申请：寝室 `gender`/`college` 与加入方一致 | `403 WRONG_GENDER` / `WRONG_COLLEGE` |

#### 3.5.2 锁顺序与上下文

confirm 采用“**先锁请求集合，再锁寝室**”的顺序（§11 有全局说明）：

```python
with transaction.atomic():
    # 1) 先无锁读取，确定参与者
    req0 = ConnectionRequest.objects.get(pk=req_id)
    user_ids = [req0.initiator_id, req0.target_id]

    # 2) 找出可能被自动取消的在途请求：双方作为发起人或目标的全部 open 请求
    ids = list(ConnectionRequest.objects.filter(
        status__in=OPEN_STATUSES,
    ).filter(
        Q(initiator_id__in=user_ids) | Q(target_id__in=user_ids)
    ).values_list("id", flat=True))

    # 3) 按 id 升序逐行加锁（确定性顺序，避免死锁）
    locked = {}
    for rid in sorted(ids, key=str):
        locked[rid] = ConnectionRequest.objects.select_for_update().get(pk=rid)

    # 4) 再锁寝室（若有）
    room = None
    if req0.room_id:
        room = Room.objects.select_for_update().get(pk=req0.room_id)

    # 5) 重读当前请求并做校验
    req = locked[req_id]
    ...
```

#### 3.5.3 第一步

`status=CONTACT_SHARED` 时：

- 双方 timestamp 均应为空；若已有任意一个非空（数据异常）→ `409 INVALID_STATE`。
- 写入本人 timestamp；`status=CONFIRMING`；`expires_at=now+48h`。
- 通知另一方 `CONFIRM_PENDING`（不包含联系方式；对方可在请求详情看到）。
- 审计 `CONNECTION_CONFIRMED_STEP1`（meta 含 `to: CONFIRMING`、`expires_at`）。
- 返回 `{status: "CONFIRMING", my_confirm_at, counterpart_confirmed: false}`。
- **不创建/加入寝室**；对方仍可 confirm 或 cancel。

#### 3.5.4 第二步与成立事务

`status=CONFIRMING` 时：

1. 校验本人 timestamp 为空；否则 `409 ALREADY_CONFIRMED`。
2. 写入本人 timestamp。
3. 按请求类型成立：
   - **人-人邀请（room=NULL）**：创建 `Room` + 两条 `RoomMember`，发起人 `OWNER`、目标 `MEMBER`，`member_count=2`。
   - **房主定向邀请（type=INVITE, room≠NULL）**：目标加入发起人的寝室。
   - **申请入寝（type=APPLY）**：发起人加入目标的寝室。
4. `req.status=CONFIRMED`；`close_reason=NULL`；两个 timestamp 均非空。
5. 关闭双方其余在途请求（`AUTO_CANCELLED`）。
6. 通知、审计、返回。

**创建寝室字段**：

| 字段 | 值 |
| --- | --- |
| `code` | 9 位数字随机码；全局唯一；碰撞重试，最多 5 次 |
| `owner` | 发起人 |
| `capacity` | `req.capacity_pref` |
| `gender` | 发起人 `gender` 快照 |
| `college` | 发起人 `college` 快照 |
| `title` | `f"{发起人.nickname}的寝室"`，截断 30 字；可后改 |
| `tags` | 双方 `tags` 去重合并，最多 8 个 |
| `status` | `FULL if capacity == 2 else RECRUITING`（2 人寝成立即满员；4/6 人寝有空位） |
| `member_count` | 2 |

**加入寝室**：

- 锁住 `Room` 后重读 `member_count`；再次断言 `status=RECRUITING` 且 `member_count < capacity`。
- 创建 `RoomMember(role=MEMBER, status=ACTIVE)`。
- `member_count += 1`。
- 若 `member_count == capacity`：`status=FULL`，并关闭该寝室其余在途请求（`FULL`，见 §4.5）；否则保持 `RECRUITING`。
- 通知寝室现有成员 `MEMBER_JOINED`；满员时通知 `ROOM_FULL`。

**关闭其余在途请求**：

```python
for other in locked.values():
    if other.id == req.id:
        continue
    if other.status not in OPEN_STATUSES:
        continue
    other.status = CANCELLED
    other.close_reason = AUTO_CANCELLED
    other.save(update_fields=["status", "close_reason", "updated_at"])
    notify_both(other, SYSTEM, {"connection_id": other.id, "reason": "AUTO_CANCELLED", "room_code": room.code if room else None})
    audit(other, "CONNECTION_AUTO_CANCELLED")
```

- 只关闭“双方其余在途请求”，不关闭其他人的请求。
- 若 `other` 有寝室且是 APPLY，不影响该寝室容量（未占位）。
- 关闭后联系方式隐藏。

#### 3.5.5 成立后的通知

| 接收者 | 类型 | payload |
| --- | --- | --- |
| 双方 | `CONFIRMED` | `{connection_id, room_code, room_title}` |
| 寝室既有成员（非新加入者） | `MEMBER_JOINED` | `{room_code, nickname, member_count, capacity}` |
| 若满员 | 寝室成员 | `ROOM_FULL` | `{room_code, capacity}` |
| 双方其余请求的对方 | `SYSTEM` | `{connection_id, reason: "AUTO_CANCELLED"}` |

#### 3.5.6 失败与回滚

- 任何守卫失败：整个事务回滚；请求保持原状态；不写寝室/成员/通知/审计。
- 请求**不自动关闭**（`ROOM_FULL`/`ROOM_LOCKED` 等）；双方可 cancel，或等 `expires_at` 过期。
- 唯一约束冲突（一人一寝、房主唯一、房间成员唯一）：捕获 `IntegrityError` → `409 ALREADY_IN_ROOM` / `409 INVALID_STATE`，整体回滚。
- 数据库死锁：按 §11.6 重试一次；仍失败返回 `503`/`409 RETRY_LATER`（前端提示重试），不写半成品。

### 3.6 过期（cron 与懒过期）

| 状态 | 到期时长 | 起点 |
| --- | --- | --- |
| `PENDING` | 48h | `created_at` |
| `CONTACT_SHARED` | 7d | `contact_shared_at`（accept 时刻） |
| `CONFIRMING` | 48h | 第一次 confirm 时刻 |

- 到期关闭：`status=EXPIRED`、`close_reason=TIMEOUT`；通知双方 `SYSTEM`；审计 `CONNECTION_EXPIRED`。
- cron `expire_connections` 每 10 分钟：`status in OPEN_STATUSES and expires_at <= now`；逐行 `select_for_update`，重读状态，幂等。
- 窗口结束时 `archive_rooms` 前先运行同命令，把该学院所有在途请求置 `EXPIRED`（不等到各自 48h/7d）。
- 懒过期（§1.3）与 cron 二选一先到；都必须在事务内加锁，避免与 confirm 并发。

### 3.7 关闭原因（close_reason）

| 值 | 产生场景 | 操作者 | 通知 |
| --- | --- | --- | --- |
| `DECLINED` | 目标拒绝 PENDING | 目标 | 发起人 `DECLINED` |
| `INITIATOR_CANCEL` | 发起人撤回 PENDING | 发起人 | 目标 `SYSTEM` |
| `END_UNDERSTANDING` | 已 accept 后任一方结束了解 | 任一方 | 对方 `SYSTEM` |
| `TIMEOUT` | 到期 / 窗口结束 | cron / 懒过期 | 双方 `SYSTEM` |
| `FULL` | 目标寝室在确认前/加入时满员，清理该寝其余请求 | 系统 | 双方 `SYSTEM` |
| `LOCKED` | 房主锁定寝室，清理该寝在途请求 | 房主/系统 | 双方 `SYSTEM` |
| `ROOM_DISSOLVED` | 寝室解散，清理该寝在途请求 | 房主/Admin | 双方 `SYSTEM` |
| `ARCHIVED` | 窗口结束归档，清理该寝在途请求 | cron | 双方 `SYSTEM` |
| `USER_DISABLED` | 用户被禁用，清理其全部在途请求 | Admin/系统 | 双方 `SYSTEM` |
| `RATE_LIMITED` | 预留：限频策略关闭请求时使用（本期不主动产生） | 系统 | — |
| `ADMIN` | 管理员强制关闭 | Admin | 双方 `SYSTEM` |
| `BLOCKED` | 任一方拉黑，清理双方在途请求 | 用户/系统 | 双方 `SYSTEM` |
| `AUTO_CANCELLED` | 组寝成立后清理双方其余在途请求 | 系统 | 双方 `SYSTEM` |

- 终态 `CONFIRMED` 的 `close_reason` 为空。
- 关闭原因只增不改；新增需在 `docs/决策记录.md` 登记并同步 Admin/前端文案。
- `FULL` 的清理只针对**目标寝室**的在途请求（APPLY / room INVITE），不影响人-人邀请。

### 3.8 联系方式可见性

| 请求状态 | 双方能否看到联系方式 | 说明 |
| --- | --- | --- |
| `PENDING` | 否 | 只能看画像/标签/prompt/匹配分 |
| `CONTACT_SHARED` | 是 | accept 后立即；双方各自 `show_*` 开关生效 |
| `CONFIRMING` | 是 | 未成立前保持可见 |
| `CONFIRMED` | 是 | 成立后保持可见（即使寝室后来解散/归档） |
| `DECLINED` / `CANCELLED` / `EXPIRED` | 否 | 关闭后隐藏；历史请求仍可看状态，不返回联系方式 |

- 只有 `GET /api/connections/:id` 的 `contact` 字段返回；列表、通知、审计、错误、日志一律不返回。
- `contact` 只包含 `show_* = true` 且值非空的渠道；全部关闭时返回 `{}`，前端显示“对方未公开联系方式”。
- Admin 仅在处理举报时可查看（需审计 `ADMIN_VIEW_CONTACT`）；不得批量导出。
- 联系方式表的 `updated_at` 变化不改变可见性；可见性只看请求状态。

### 3.9 限频与反骚扰

| 规则 | 值 | 计数口径 |
| --- | --- | --- |
| 在途请求上限 | 3 | 当前用户作为 `initiator` 的 open 请求数 |
| 每日发起上限 | 10 | 当前用户作为 `initiator`、`created_at` 在 `Asia/Shanghai` 当日 |
| 被拒冷却 | 24h | 同一对用户（任一方向）最近一条 `DECLINED` 的 `updated_at` 起算 |
| 拉黑 | 立即 | 双方在途请求全部 `BLOCKED`；广场/匹配/搜索互不可见；不能创建新请求 |
| 举报 | 人工 | 只落 `Report`，不自动封禁；Admin 处理并审计 |

- 限频只在**创建**时检查；accept/decline/cancel/confirm 不限频（否则被骚扰方无法退出）。
- 创建事务内锁 `User` 行后计数，避免并发突破上限。
- 被拒冷却按“同一对用户”双向生效：A 被 B 拒绝后，B 也不能在 24h 内向 A 发起。
- 拉黑不影响已成立的寝室（室友关系保留），但双方不再出现在彼此的匹配/广场/搜索；如需分开走退出/移除/解散。

### 3.10 管理员动作

| 动作 | 允许状态 | 结果 | 审计 |
| --- | --- | --- | --- |
| 关闭请求 | 任意在途 | `CANCELLED` / `ADMIN`；通知双方 | `CONNECTION_ADMIN_CLOSED` |
| 强制解散寝室 | 任意非终态 | 同房主解散；成员 `LEFT`/`DISSOLVED`；清理请求/转让 | `ROOM_FORCE_DISSOLVED` |
| 禁用用户 | 任意 | 契约见 §12.7 | `USER_DISABLED` |
| 查看联系方式 | 举报处理 | 只读；不写业务状态 | `ADMIN_VIEW_CONTACT` |
| 修改性别/学院 | 任意 | 允许，但不改历史寝室；后续写操作按新值校验 | `USER_IDENTITY_CHANGED` |

- Admin 不得代替用户 accept/confirm；不得把请求直接改成 `CONFIRMED`。
- Admin 强制解散/关闭不受时间窗限制（§1.4），但必须写审计和通知。

## 4. Room（寝室）

### 4.1 字段与状态

| 字段 | 规则 |
| --- | --- |
| `code` | 9 位数字；全局唯一；创建后不可改；公开分享页使用 |
| `owner` | 创建者；同时必须是 `RoomMember(role=OWNER,status=ACTIVE)`（非终态） |
| `capacity` | 2/4/6；创建后不可改；不可扩容 |
| `member_count` | 活跃成员数快照；非归档/非解散时与 ACTIVE 成员数一致 |
| `gender` | 创建时快照；`MALE/FEMALE`；不可改 |
| `college` | 创建时快照；不可改 |
| `title` | 默认 `"{nickname}的寝室"`，≤30 字；房主可改（非终态） |
| `tags` | JSON 数组，≤8 个；人-人建寝时双方标签合并去重 |
| `status` | `RECRUITING` / `FULL` / `LOCKED` / `ARCHIVED` / `DISSOLVED` |
| `archived_at` | 归档时刻；终态 |

### 4.2 不变量

1. `1 <= member_count <= capacity`；`DISSOLVED` 时 `member_count=0`；`ARCHIVED` 时保留归档快照。
2. 非 `ARCHIVED/DISSOLVED` 房间：`member_count == count(RoomMember.status=ACTIVE)`。
3. 非终态房间：`owner` 必须是唯一 `ACTIVE + OWNER` 成员。
4. 所有 ACTIVE 成员 `gender == room.gender`、`college == room.college`。
5. 一个用户最多一个 `ACTIVE RoomMember`（归档成员不算）。
6. `RECRUITING` 必有空位（`member_count < capacity`）；`FULL` 必满员（`==`）；`LOCKED` 必未满且未归档/解散。
7. `capacity` 只能 2/4/6；`member_count` 不得超容量。
8. 房间 `code` 唯一；`status` 只按 §2.2 迁移。

### 4.3 创建（仅由人-人确认触发）

- 没有公开的 `POST /api/rooms`；寝室只能由 `ConnectionRequest(type=INVITE, room=NULL)` 的双方 confirm 成立时创建。种子/Admin 数据可通过管理命令创建，但必须满足不变量。
- 创建字段见 §3.5.4。
- `member_count=2`；`status = FULL if capacity == 2 else RECRUITING`。
- 通知：双方 `CONFIRMED`；若 `capacity=2`，双方同时收到 `ROOM_FULL`（房间已满，仅作状态提示）。
- 审计：`ROOM_CREATED`，meta `{connection_id, capacity}`。

### 4.4 加入（仅由 confirm 触发）

- 没有公开的 `POST /api/rooms/:code/join`；加入只能由 `INVITE(room≠NULL)` 或 `APPLY` 的双方 confirm 成立时发生。
- 事务内锁 `Room`，重读 `member_count/status`，再次断言 `RECRUITING` + 空位。
- 创建 `RoomMember(role=MEMBER,status=ACTIVE)`；`member_count+1`。
- 若达到容量：`status=FULL`，执行 §4.5 的满员清理。
- 通知既有成员 `MEMBER_JOINED`；审计 `MEMBER_JOINED`。
- 若加入方已有 ACTIVE 寝室：`409 ALREADY_IN_ROOM`，整体回滚。

### 4.5 满员清理（FULL）

当一次加入使 `member_count == capacity`：

1. `Room.status=FULL`。
2. 关闭该寝室所有仍在途的请求（`type=INVITE AND room=本寝`、`type=APPLY AND room=本寝`）：
   - `status=CANCELLED`、`close_reason=FULL`；
   - 通知双方 `SYSTEM`，payload `{connection_id, reason: "FULL", room_code}`；
   - 审计 `CONNECTION_CLOSED_FULL`。
3. 通知寝室成员 `ROOM_FULL`（payload `{room_code, capacity}`）。
4. 审计 `ROOM_FULL`。

> 目的：避免“房间已满但请求还挂着”的死状态；被关闭的请求不占名额，双方可另找寝室。**不关闭**人-人邀请（room=NULL）；它们与具体寝室无关。

### 4.6 锁定 / 解锁

**锁定**（房主）：

- 条件：`Room.status=RECRUITING`；房主是 ACTIVE OWNER；窗口开放。
- 结果：`LOCKED`；关闭该寝室所有在途请求（`close_reason=LOCKED`）；通知相关方 `ROOM_LOCKED`；审计 `ROOM_LOCKED`。
- 锁定后：不可 accept/confirm 入寝；不可申请/被邀请；仍可退出/移除/转让/解散/解锁；不参与广场。
- 被关闭的请求不会因解锁自动恢复；用户需重新发起。

**解锁**（房主）：

- 条件：`Room.status=LOCKED`；窗口开放。
- 结果：`RECRUITING`（锁定时必有空位；期间成员只减不增，仍有空位）；不发送通知（房主主动操作），只写审计 `ROOM_UNLOCKED`。
- 不恢复已关闭请求。

### 4.7 退出 / 移除成员

| 动作 | 操作者 | 条件 | 结果 |
| --- | --- | --- | --- |
| 退出 | 非房主 ACTIVE 成员 | 窗口开放；房间非终态 | `LEFT/LEFT`；`member_count-1`；状态回退；取消指向该成员的 pending 转让 |
| 移除 | 房主 | 目标是 ACTIVE 非房主成员；窗口开放 | `REMOVED/REMOVED`；`member_count-1`；状态回退；取消指向该成员的 pending 转让 |

- 房主不能退出：`409 OWNER_MUST_TRANSFER_OR_DISSOLVE`。
- `FULL` 成员退出/被移除 → `RECRUITING`；`RECRUITING` 保持；`LOCKED` 保持 `LOCKED`（有空位但暂停招募）。
- 退出/移除后，该用户不再占用一人一寝，可在窗口开放时重新创建/加入。
- 通知：房主/成员 `MEMBER_LEFT`；被移除者 `MEMBER_LEFT`；审计 `MEMBER_LEFT` / `MEMBER_REMOVED`。
- 不恢复该寝室此前因满员/锁定关闭的请求。

### 4.8 解散（DISSOLVED）

- 操作者：房主（窗口开放）或 Admin（不受窗口限制）。
- 条件：`RECRUITING/FULL/LOCKED`；`DISSOLVED/ARCHIVED` 不可再解散。
- 事务（锁顺序见 §11）：
  1. 锁房间；
  2. 关闭该寝室全部在途请求（`ROOM_DISSOLVED`）；
  3. 关闭所有涉及 ACTIVE 成员的在途请求（防御性；正常不应存在）；
  4. 取消 pending 转让（`CANCELLED`）；
  5. 所有 `ACTIVE` 成员 → `LEFT`，`reason=DISSOLVED`，`left_at=now`；
  6. `member_count=0`；`status=DISSOLVED`；`archived_at=now`；
  7. 通知所有成员 `ROOM_DISSOLVED`；审计 `ROOM_DISSOLVED` / `ROOM_FORCE_DISSOLVED`。
- 解散释放全部成员；成员可在窗口开放时重新组寝。
- 房间详情保留只读历史（成员可查）；公开分享页 404/410。

### 4.9 归档（ARCHIVED）

- 触发：cron `archive_rooms`，该学院 `TimeWindow.end_at <= now`；或 Admin 归档修复（审计）。
- 条件：`RECRUITING/FULL/LOCKED`；已 `DISSOLVED` 的寝室不再归档（保持 DISSOLVED，避免覆盖终止原因）。
- 事务：
  1. 锁房间；
  2. 关闭该寝室在途请求（`ARCHIVED`）；
  3. 取消 pending 转让（`CANCELLED`）；
  4. 所有 `ACTIVE` 成员 → `ARCHIVED`，`reason=ARCHIVED`；
  5. `status=ARCHIVED`；`archived_at=now`；`member_count` 保留归档快照；
  6. 通知成员 `ROOM_ARCHIVED`；审计 `ROOM_ARCHIVED`。
- **归档成员不再占用一人一寝**（手册 D5 已同步修正）：成员可在新时间窗重新创建/加入寝室。
- 归档后房间只读：不能退出/移除/转让/解散/编辑；成员仍可在“我的寝室”查看最终名单。
- 不提供“取消归档”；新窗口不会复活旧房间。

### 4.10 读可见性（与状态相关）

- 广场：仅 `RECRUITING`（`FULL/LOCKED/ARCHIVED/DISSOLVED` 不出现）。
- 寝室详情：本学院同性别登录用户可看招募中/满员/锁定房间的公开字段；成员/历史成员可看本寝完整字段。
- 公开分享 `/room/:code`：仅 `RECRUITING/FULL/LOCKED` 返回有限字段（标题/人数/容量/标签/成员昵称/默认头像）；`ARCHIVED/DISSOLVED` 一律 `404 ROOM_NOT_FOUND`（不泄露历史）；任何状态都不返回联系方式。
- 搜索/匹配不返回已归档/已解散房间。

## 5. RoomMember（寝室成员）

### 5.1 字段

| 字段 | 规则 |
| --- | --- |
| `room` / `user` | 联合唯一；同一房间同一用户只有一条记录 |
| `role` | `OWNER` / `MEMBER`；一个房间同时只能有一个 ACTIVE OWNER |
| `status` | `ACTIVE` / `LEFT` / `REMOVED` / `ARCHIVED` |
| `reason` | `LEFT` / `REMOVED` / `DISSOLVED` / `USER_DISABLED` / `ARCHIVED`；ACTIVE 为空 |
| `created_at` / `left_at` | 进入/离开时刻（`created_at` 即加入时间）；ARCHIVED 的 `left_at` 为归档时刻 |

### 5.2 不变量

1. 一个用户最多一个 `ACTIVE` 成员关系（部分唯一索引 `user where status=ACTIVE`）。
2. 同一房间同一用户只有一条记录；`LEFT/REMOVED/ARCHIVED` 不可回流为 ACTIVE。
3. 非终态房间的 `owner` 必须对应唯一 `ACTIVE + OWNER`。
4. `member_count` 与非归档/非解散房间的 ACTIVE 成员数一致。
5. `ARCHIVED` 成员不占一人一寝；不代表可回房。

### 5.3 迁移

| 当前 | 动作 | 操作者 | 目标 | 副作用 |
| --- | --- | --- | --- | --- |
| `ACTIVE` | 退出 | 本人（非房主） | `LEFT` | `reason=LEFT`；`left_at`；`member_count-1`；房间状态回退；通知 |
| `ACTIVE` | 移除 | 房主 | `REMOVED` | `reason=REMOVED`；`left_at`；`member_count-1`；通知 |
| `ACTIVE` | 解散 | 房主/Admin | `LEFT` | `reason=DISSOLVED`；`left_at`；`member_count` 由房间事务归零 |
| `ACTIVE` | 禁用 | Admin | `LEFT` | `reason=USER_DISABLED`；见 §12.7 |
| `ACTIVE` | 归档 | cron | `ARCHIVED` | `reason=ARCHIVED`；`left_at=now`；不占一人一寝 |
| `LEFT/REMOVED/ARCHIVED` | 任意 | — | 不可变 | 历史只读 |

- 退出/移除后重新加入**同一房间**：不允许（联合唯一 + 不可回流）。可加入其他房间。
- 成员被移除/退出不删除记录；审计与历史保留。
- 房主转让后，原房主变为 `MEMBER`（同一条记录），新房主 `MEMBER → OWNER`；`created_at` 不变。

## 6. RoomTransfer（房主转让）

### 6.1 字段与状态

| 字段 | 规则 |
| --- | --- |
| `room` | 被转让寝室；非终态 |
| `from_owner` | 发起时的房主 |
| `to_member` | 目标成员；必须是 ACTIVE 非房主成员 |
| `status` | `PENDING` / `ACCEPTED` / `DECLINED` / `CANCELLED` / `EXPIRED` |
| `expires_at` | 创建 + 24h |
| `created_at` / `updated_at` | 审计 |

- 同一寝室同时最多一条 `PENDING` 转让（部分唯一索引 `room where status=PENDING`）。
- 状态迁移见 §2.4；终态不可回流。

### 6.2 发起

- 操作者：当前 ACTIVE 房主；窗口开放。
- 条件：房间 `RECRUITING/FULL/LOCKED`；目标为 ACTIVE 非房主成员；无 pending 转让；目标未在别的 pending 转让中（同寝唯一已覆盖）。
- 结果：`PENDING`、`expires_at=now+24h`；通知目标 `TRANSFER_RECEIVED`；审计 `TRANSFER_CREATED`。
- 不影响房主身份、成员数、房间状态。

### 6.3 接受 / 拒绝 / 取消 / 过期

| 动作 | 操作者 | 条件 | 结果 |
| --- | --- | --- | --- |
| 接受 | `to_member` | `PENDING`、未过期、窗口开放、双方仍 ACTIVE、from_owner 仍是房主、房间非终态 | 角色交换；`ACCEPTED` |
| 拒绝 | `to_member` | `PENDING`、未过期 | `DECLINED`；通知房主 |
| 取消 | `from_owner` | `PENDING` | `CANCELLED`；通知目标 |
| 过期 | cron | `expires_at <= now` | `EXPIRED`；通知双方 |

**接受事务**（锁顺序：先 `Room`，再 `RoomTransfer`，再成员行）：

```python
with transaction.atomic():
    t0 = RoomTransfer.objects.get(pk=transfer_id)          # 无锁读取定位
    room = Room.objects.select_for_update().get(pk=t0.room_id)
    t = RoomTransfer.objects.select_for_update().get(pk=transfer_id)
    # 重读并校验：PENDING、未过期、from_owner 仍 owner、to_member 仍 ACTIVE MEMBER
    old_owner_member = RoomMember.objects.select_for_update().get(room=room, user=t.from_owner)
    new_owner_member = RoomMember.objects.select_for_update().get(room=room, user=t.to_member)
    old_owner_member.role = MEMBER
    old_owner_member.save(update_fields=["role"])
    new_owner_member.role = OWNER
    new_owner_member.save(update_fields=["role"])
    room.owner = t.to_member
    room.save(update_fields=["owner"])
    t.status = ACCEPTED
    ...
```

- 必须先降旧房主为 `MEMBER`，再升目标为 `OWNER`，避免“两个 ACTIVE OWNER”唯一约束冲突。
- `member_count`、房间 `status` 不变。
- 通知：双方 `TRANSFER_ACCEPTED`；审计 `TRANSFER_ACCEPTED`。

### 6.4 自动取消

以下事件将 `PENDING` 转让置 `CANCELLED` 并通知双方：

- 寝室解散/归档；
- 目标成员退出/被移除；
- 房主被禁用/房间被强制解散（由房间事务处理）；
- 房主发起新的转让（应被 `409 TRANSFER_EXISTS` 阻止，不会发生）。

不自动取消：寝室锁定/满员/成员加入（转让与招募并行不冲突）。

## 7. TimeWindow（组寝时间窗）

### 7.1 模型与语义

| 字段 | 规则 |
| --- | --- |
| `college` | 学院；唯一（一个学院一个当前窗口） |
| `start_at` / `end_at` | 窗口起止；`start_at < end_at`；UTC 存储 |
| `note` | 运营备注 |

- **未配置 = 关闭**：查询不到该学院窗口，或 `now < start_at`，或 `now >= end_at`，均视为关闭。
- 窗口只约束**组寝写操作**（创建请求/accept/decline/cancel/confirm、锁定/解锁/退出/移除/解散/转让）。注册、登录、资料/问卷编辑、举报、拉黑、通知已读不受影响。
- 窗口关闭时：只读；已存在的寝室展示；cron 归档。

### 7.2 开放判定

```python
def is_window_open(college, now):
    w = TimeWindow.objects.filter(college=college).first()
    return bool(w and w.start_at <= now < w.end_at)
```

- 每次写操作实时查询；不使用长缓存；可在请求级缓存 1 秒，但事务内必须重读。
- 前端只做展示（倒计时/禁用按钮），最终以服务端为准。

### 7.3 管理

- Admin 创建/编辑窗口；字段校验 `start_at < end_at`；同一学院唯一。
- 不提供删除：需停用时把 `end_at` 改到过去；下一个归档周期生效。
- 缩短窗口：已成立的寝室不自动解散；到新 `end_at` 后归档。
- 延长窗口：已归档寝室不复活；只影响尚未归档的房间和后续写操作。
- 修改窗口写审计 `WINDOW_CREATED` / `WINDOW_UPDATED`。

### 7.4 结束处理（cron）

`archive_rooms` 每 10 分钟（与过期命令同批）：

1. 找出 `end_at <= now` 的窗口（按学院）。
2. 先运行 `expire_connections`，把该学院所有在途请求置 `EXPIRED/TIMEOUT`（幂等）。
3. 再把这些学院的 `RECRUITING/FULL/LOCKED` 房间归档：关闭残留请求（`ARCHIVED`）、取消转让、成员转 `ARCHIVED`、房间 `ARCHIVED`、通知、审计。
4. 已 `DISSOLVED` 的房间跳过归档（保持解散原因）。

- 命令可重复执行；已归档/已终态跳过。
- 归档与 confirm 并发：靠锁顺序（§11）保证“要么 confirm 先完成、要么归档先完成”；不会出现半归档。

### 7.5 提醒（WINDOW_CLOSING）

- 结束前 7/3/1 天各提醒一次；由每日 cron 发送。
- 接收者：该学院有 ACTIVE 寝室或 open 请求的用户。
- 去重：同一用户 + 同一 `end_at` + `WINDOW_CLOSING` 已存在则跳过；payload `{college, end_at, days_left}`。
- 提醒不改变状态；用户仍可继续操作直到窗口关闭。

## 8. 通知矩阵

### 8.1 通用规则

- 站内信：`Notification(user, type, payload, read_at, created_at)`；无发件人字段；type 为字符串枚举（见 §8.2）。
- **与业务同事务**：状态变更、通知、审计三者同生共死；通知插入失败则整个动作回滚（手册 §3.6 不变量）。
- payload 只放 id/昵称/房间号/原因等非敏感字段；**绝不**放 QQ/微信/手机号、邮箱、token、真名、IP、User-Agent。
- 一个事件可能生成多行（每个接收者一行）；同一用户对同一事件只生成一行。
- 已读：`GET /api/notifications`、`GET /api/notifications/unread-count`、`POST /api/notifications/:id/read`、`POST /api/notifications/read-all`；前端 20s 轮询未读数。
- 保留：已读通知 90 天后由 cron 清理；未读保留 180 天；审计不受影响。
- 去重：除窗口提醒外，每个业务事件天然只发生一次（状态机幂等），不需要额外去重键；窗口提醒按 §7.5 查询去重。
- 通知不改变业务状态；点击通知只做前端路由，不直接执行写动作。

### 8.2 事件矩阵

| # | 事件 | 触发点 | 接收者 | `type` | payload 关键字段 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| N-01 | 收到邀请/申请 | 创建请求成功 | `target` | `CONNECTION_RECEIVED` | `connection_id`、`from_nickname`、`type`、`room_code?` | 仅目标；不泄露联系方式 |
| N-02 | 对方同意（第一步） | accept 成功 | `initiator` | `CONTACT_SHARED` | `connection_id` | 目标刚操作，不重复通知 |
| N-03 | 对方已确认（第二步） | 第一次 confirm 成功 | 尚未确认方 | `CONFIRM_PENDING` | `connection_id` | 催促第二步；不改变请求状态 |
| N-04 | 组寝成立 | 第二步 confirm 成功 | 双方 | `CONFIRMED` | `connection_id`、`room_code`、`room_title` | 双方同一事件各一行 |
| N-05 | 被拒绝 | decline 成功 | `initiator` | `DECLINED` | `connection_id` | 关闭原因 `DECLINED` |
| N-06 | 请求取消/过期/被系统关闭 | cancel / 懒过期 / cron / 满员清理 / 锁定清理 / 解散 / 归档 / 拉黑 / 禁用 / Admin | 另一方 | `SYSTEM` | `connection_id`、`reason`、`room_code?` | `reason` 取 `close_reason`；双方都收到时各一行 |
| N-07 | 新成员加入 | 加入寝室成立 | 寝室既有成员（不含新成员） | `MEMBER_JOINED` | `room_code`、`nickname`、`member_count`、`capacity` | 满员时另发 N-08 |
| N-08 | 房间满员 | `member_count == capacity` | 全体成员 | `ROOM_FULL` | `room_code`、`capacity` | 仅状态提示，不能入寝 |
| N-09 | 成员退出/被移除 | leave/remove 成功 | 剩余成员 + 当事人 | `MEMBER_LEFT` | `room_code`、`nickname`、`reason` | 当事人也收到（确认结果） |
| N-10 | 房间锁定 | owner lock 成功 | 全体成员 | `ROOM_LOCKED` | `room_code` | 被关闭请求方走 N-06 |
| N-11 | 房间解散 | owner/Admin dissolve 成功 | 全体成员 | `ROOM_DISSOLVED` | `room_code`、`reason` | Admin 时 `reason=ADMIN` |
| N-12 | 房间归档 | cron archive 成功 | 全体成员 | `ROOM_ARCHIVED` | `room_code`、`archived_at` | 归档后只读 |
| N-13 | 收到转让 | 创建转让成功 | `to_member` | `TRANSFER_RECEIVED` | `room_code`、`transfer_id`、`from_nickname`、`expires_at` | 24h 有效 |
| N-14 | 转让被接受 | accept 转让成功 | 双方 | `TRANSFER_ACCEPTED` | `room_code`、`transfer_id` | 角色已交换 |
| N-15 | 转让被拒绝 | decline 转让成功 | `from_owner` | `TRANSFER_DECLINED` | `room_code`、`transfer_id` | — |
| N-16 | 转让过期 | cron/lazy | 双方 | `TRANSFER_EXPIRED` | `room_code`、`transfer_id` | 24h 到期 |
| N-17 | 转让取消 | 房主取消/房间解散/目标离开 | 双方 | `TRANSFER_CANCELLED` | `room_code`、`transfer_id`、`reason` | 不改变房主 |
| N-18 | 窗口即将关闭 | 每日 cron | 该学院有 ACTIVE 房或 open 请求的用户 | `WINDOW_CLOSING` | `college`、`end_at`、`days_left` | 7/3/1 天各一次；查询去重 |
| N-19 | 举报处理结果（可选） | Admin 处理举报 | 举报人 | `SYSTEM` | `report_id`、`status` | 本期可选；不自动封禁 |

> 说明：N-06 用统一 `SYSTEM` 类型承载所有“非正常完成”的关闭，前端按 `reason` 显示不同文案；不再为每个原因新增 type，避免枚举膨胀。

### 8.3 payload 约定

```json
{
  "connection_id": 123,
  "room_code": "482913756",
  "from_nickname": "小林",
  "reason": "FULL",
  "member_count": 4,
  "capacity": 4,
  "archived_at": "2026-12-01T16:00:00Z",
  "transfer_id": 9,
  "expires_at": "2026-11-16T10:00:00Z",
  "college": "计算机学院",
  "end_at": "2026-12-01T16:00:00Z",
  "days_left": 3
}
```

- 所有时间 ISO8601 UTC；前端本地化。
- 缺失字段省略，不写 `null` 占位（除明确需要）。
- `nickname` 是用户昵称，不是真名；`from_nickname` 仅用于邀请/转让识别。
- 通知标题由后端按 `type` + `reason` 生成；前端不拼接用户输入到 HTML（防 XSS）。
- 通知列表按 `created_at DESC, id DESC` 分页；未读数单独轻量接口。

## 9. 审计事件

### 9.1 AuditLog 模型约定

| 字段 | 规则 |
| --- | --- |
| `id` | BigAutoField |
| `actor` | FK User，可空；`null` = 系统/cron |
| `action` | 字符串枚举，见 §9.2；只增不改 |
| `target_type` | `connection` / `room` / `room_member` / `transfer` / `time_window` / `user` / `report` / `invite_code` |

- 保留期：永久（审计用途）；备份包含。
- 与业务同事务：状态变更没有审计 = 实现缺陷。
- 索引：`(target_type, target_id)`、`(actor, created_at)`、`(action, created_at)`、`request_id`。

## 10. 错误码与 HTTP 状态

### 10.1 统一响应

所有业务错误返回：

```json
{
  "code": "ROOM_FULL",
  "message": "房间已满员",
  "detail": {"room_code": "482913756"}
}
```

- HTTP 状态表达类别；`code` 供前端分支；`message` 中文可直接展示；`detail` 为对象或 `null`。
- 字段校验错误（DRF serializer）统一为：

```json
{
  "code": "VALIDATION_ERROR",
  "message": "请求参数不合法",
  "detail": {"field": ["错误说明"]}
}
```

- 不返回堆栈、SQL、内部路径；500 响应带 `request_id` 便于查日志。
- 错误响应**不得**包含联系方式、邮箱、真名、token；即使动作涉及这些表。

### 10.4 幂等错误的语义

- 重复创建同一请求 → `409 DUPLICATE_REQUEST`（不返回已存在请求的 id，避免探测；前端刷新列表）。
- 重复 confirm 同一步 → `409 ALREADY_CONFIRMED`；不重复建寝/入寝。
- 重复 accept/decline/cancel → `409 INVALID_STATE` / `REQUEST_CLOSED`；不重复通知。
- 重复锁定/解锁 → `409 INVALID_STATE`；不重复清理。
- 重复转让接受 → `409 INVALID_STATE`；不重复交换角色。
- 网络超时后客户端可重试：若第一次已提交，第二次返回上述 409；前端以“刷新后状态”为准，不显示为系统错误。

## 11. 锁顺序、并发与幂等

### 11.1 事务边界

- 每个写动作 = 一个 `transaction.atomic()`；状态、成员、请求、转让、通知、审计全部在同一事务。
- 事务内**禁止**外部调用（HTTP、邮件、短信、对象存储）；本期只有 DB 写入，满足。
- 事务尽量短：不 sleep、不重试业务、不做大查询；锁获取后只做必要重读与更新。
- 视图/序列化器不写库；写动作只调用 service。
- 隔离级别：PostgreSQL 默认 `READ COMMITTED`；不依赖快照，依赖行锁 + 约束。
- 不在事务外调用 `select_for_update()`（Django 会抛 `TransactionManagementError`）。

### 11.2 全局锁顺序

所有组寝写动作按以下顺序获取锁；**只能跳过后面的锁，不能颠倒**：

| 顺序 | 对象 | 获取方式 | 说明 |
| --- | --- | --- | --- |
| 1 | `TimeWindow`（当前学院） | `select_for_update()` 单行 | 冻结窗口，避免动作中途窗口被改；无记录=关闭，不加锁 |
| 2 | `User`（参与者） | `select_for_update()`，`id` 升序 | 双方/成员/目标；防反向创建、一人两寝、限频并发 |
| 3 | `ConnectionRequest`（将被读/关闭的 open 行） | `select_for_update()`，`id` 升序 | 参与者相关 + 目标寝室相关；必须先于 Room |
| 4 | `Room` | `select_for_update()` 单行 | 容量/状态/房主 |
| 5 | `RoomTransfer` | `select_for_update()` 单行 | 同寝 pending |
| 6 | `RoomMember` | `select_for_update()`，`user_id` 升序 | 角色交换、退出/移除、归档 |
| 7 | `Notification` / `AuditLog` | 仅 INSERT | 不参与锁顺序 |

**为什么请求必须先于 Room**：confirm 走“锁请求 → 锁 Room”；如果满员清理/锁定/解散先锁 Room 再锁请求，会与 confirm 形成环。因此房间类动作在锁 Room 之前，先锁“该寝在途请求 + 成员相关在途请求”。

**为什么 User 先于全部**：反向创建（A→B 与 B→A）必须锁同一对 User 行再双向查询；一人两寝、限频计数也靠 User 行串行化。

**为什么 Transfer 在 Room 之后**：转让接受要读房主/成员并改 Room.owner；与解散/退出统一为 Room → Transfer → Member，避免与“锁 Transfer 再锁 Room”的路径成环。

### 11.3 典型动作的加锁清单

| 动作 | 锁 1 Window | 锁 2 Users | 锁 3 Requests | 锁 4 Room | 锁 5 Transfer | 锁 6 Members |
| --- | --- | --- | --- | --- | --- | --- |
| 创建请求 | 是 | 双方 | 双方 open | 目标寝（room 非空时，仅读锁） | — | — |
| accept | 是 | 双方 | 本条 | room 非空时锁 | — | — |
| decline / cancel | 是 | 双方 | 本条 | — | — | — |
| confirm 第一步 | 是 | 双方 | 双方 open | room 非空时锁 | — | — |
| confirm 第二步（建寝） | 是 | 双方 | 双方 open | —（新建） | — | 插入两条 |
| confirm 第二步（入寝） | 是 | 双方 | 双方 open + 该寝 open | 是 | — | 插入一条 |
| 锁定/解锁 | 是 | 房主 | 该寝 open | 是 | — | — |
| 退出/移除 | 是 | 操作者+目标 | —（不关请求） | 是 | 是（取消） | 是 |
| 解散 | 是 | 全部成员 | 该寝 open + 成员 open | 是 | 是 | 是 |
| 归档（cron） | 否 | 全部成员 | 该寝 open + 成员 open | 是 | 是 | 是 |
| 转让发起 | 是 | 房主+目标 | — | 是 | 查/插 | 是（校验目标） |
| 转让接受 | 是 | 房主+目标 | — | 是 | 是 | 是 |
| 转让拒绝/取消 | 是 | 操作者 | — | 是 | 是 | — |
| 禁用用户（Admin） | 否 | 被禁用者 | 其全部 open | 其房/所在寝 | 是 | 是 |

> “该寝 open”指 `status in OPEN_STATUSES AND room_id = 本寝` 的请求；“成员 open”指 `initiator_id` 或 `target_id` 属于本寝 ACTIVE 成员的 open 请求。查询后按 `id` 升序逐个 `select_for_update`。

### 11.4 加锁辅助函数（P2 实现约定）

```python
def lock_users(ids):
    qs = User.objects.select_for_update().filter(id__in=sorted(set(ids))).order_by("id")
    return list(qs)

def lock_requests(ids):
    qs = ConnectionRequest.objects.select_for_update().filter(id__in=sorted(set(ids))).order_by("id")
    return list(qs)

def lock_window(college):
    return TimeWindow.objects.select_for_update().filter(college=college).first()

def lock_room(room_id):
    return Room.objects.select_for_update().get(pk=room_id)

def lock_members(room_id, user_ids=None):
    qs = RoomMember.objects.select_for_update().filter(room_id=room_id)
    if user_ids:
        qs = qs.filter(user_id__in=sorted(set(user_ids)))
    return list(qs.order_by("user_id"))
```

- 先查 id 列表（无锁），再按顺序批量加锁；加锁后**重读**对象并重新校验状态。
- 不要 `select_for_update()` 后立即 `count()` 做容量判断；用 `Room.member_count` 字段。
- `select_for_update()` 默认等待；不用的 `nowait` 仅用于 cron 的 `skip_locked` 批量扫描。

### 11.5 死锁与重试

- 捕获 PostgreSQL `deadlock_detected`（SQLSTATE `40P01`）与 `serialization_failure`（`40001`）。
- 整个事务重试，最多 3 次；退避 20ms / 50ms / 100ms + 随机抖动；每次重试重新执行完整 service（重新校验、重新加锁）。
- 重试只对可重试的数据库异常；业务 `Conflict`（409）不重试。
- 3 次仍失败：返回 `500 INTERNAL_ERROR`，记录 `request_id` + 动作 + 参与方 id；不返回 SQL。
- `IntegrityError`（唯一约束/Check）不重试，映射为对应业务错误：`DUPLICATE_REQUEST`、`ALREADY_IN_ROOM`、`TRANSFER_EXISTS`、`ALREADY_CONFIRMED` 等；无法映射的按 500 记录。
- 设 `statement_timeout=10s` 防止单个事务长期占锁；超时返回 500 并记录（不自动重试，避免放大）。
- 事务内不捕获异常后继续写；一律抛出，让 atomic 回滚。

### 11.6 幂等性

| 动作 | 幂等策略 |
| --- | --- |
| 创建请求 | 部分唯一索引（同方向 pair open）+ User 锁 + 反向查询；重复 409 |
| accept | 状态机 + 行锁；重复 409 `INVALID_STATE` |
| confirm 第一步 | 条件更新 `WHERE status=CONTACT_SHARED AND initiator_confirm_at IS NULL`（或 target 对应列）；影响行数=0 → 重读判断 `ALREADY_CONFIRMED`/`INVALID_STATE` |
| confirm 第二步 | 同上；另一 timestamp 条件；事务内只建一次寝 |
| 锁定/解锁/解散/归档 | 状态机 + 行锁；已终态 409/跳过 |
| 退出/移除 | `RoomMember.status=ACTIVE` 条件更新；已非 ACTIVE → 409 |
| 转让接受/拒绝 | 状态机 + 行锁；重复 409/`TRANSFER_EXPIRED` |
| cron 过期 | `status in OPEN and expires_at<=now` + 行锁重读；已关闭跳过 |
| cron 归档 | 只处理非终态；已归档/解散跳过 |
| 通知 | 业务事件只发生一次；窗口提醒查询去重（§7.5） |
| 审计 | 与业务同事务；不会重复写（除非业务重试，事务回滚后重写一次） |

- 不要求客户端传 `Idempotency-Key`；前端在超时后统一“刷新当前状态”，不要盲目重放写请求。
- 所有 `GET` 天然幂等；未读计数可缓存 1–2s，但写后前端主动刷新。

### 11.7 并发场景与预期

| # | 场景 | 预期 |
| --- | --- | --- |
| L-01 | 同一用户双击 confirm 第二步 | 第一次成功；第二次 409 `ALREADY_CONFIRMED`；只建一个寝 |
| L-02 | 双方同时 confirm 第二步 | 串行：一方先完成第一步/第二步，另一方重读后完成剩余步骤；最终一个寝、两条成员 |
| L-03 | A→B 与 B→A 同时创建 | User 行锁串行；先到者成功，后到者 409 `DUPLICATE_REQUEST`；只有一条 open |
| L-04 | 两人抢最后一个空位 | Room 行锁串行；先 confirm 者成功并转 FULL；后到者 409 `ROOM_FULL`；`member_count == capacity` |
| L-05 | accept 与 initiator cancel 同时 | 先锁请求者成功；后到者 409 `INVALID_STATE`；联系方式不会在关闭后泄露 |
| L-06 | 锁定 与 confirm 第二步同时 | 先锁 Room 者成功；若锁定先，confirm 409 `ROOM_LOCKED`，请求被锁定清理；若 confirm 先，锁定看到房间已满/仍 RECRUITING 按状态处理 |
| L-07 | 满员清理 与 新请求创建同时 | 新请求需锁房主 User；满员事务持房主 User + Room；新请求等待后看到 FULL → 409；不会插入“已满还 open”的请求 |
| L-08 | 归档 与 confirm 同时 | 先锁 Room 者成功；归档先则 confirm 409 `INVALID_STATE`/`ROOM_ARCHIVED`；confirm 先则归档看到新成员并正常归档 |
| L-09 | 转让接受 与 目标退出同时 | 退出锁 Room→Transfer→Member；接受同序；先到者成功；后到者 409（转让已取消/成员已非 ACTIVE） |
| L-10 | 解散 与 confirm 同时 | 同 L-06/L-08；解散后请求 `ROOM_DISSOLVED`，confirm 409 |
| L-11 | 拉黑 与 创建请求同时 | 拉黑清理锁用户/请求；创建锁用户；先到者成功；后到者 403 `BLOCKED` 或 409 |
| L-12 | cron 两次同时跑 | 行锁 + 状态重读；第二次跳过已终态，不重复通知/审计 |
| L-13 | 同一对用户历史请求已关闭后再创建 | open 唯一索引不阻止；允许（除非 24h 冷却/拉黑） |
| L-14 | 房主转让后立即退出 | 转让接受后原房主是 MEMBER，可退出；房间 owner 已是目标，退出不影响 owner |
| L-15 | 成员退出使 FULL→RECRUITING 同时有人申请 | Room 锁串行；退出先则新申请可成功；申请先则房间仍 FULL → 409；不会超容量 |

| R-01 | 人-人建寝字段 | 容量 4 成立 | code 9 位；owner=A；capacity=4；gender/college 快照；member_count=2；status=RECRUITING；tags 合并去重≤8 |
| R-02 | 容量 2 建寝 | 容量 2 成立 | status=FULL；member_count=2；不能再邀请 |
| R-03 | 抢最后空位（并发） | 两个申请者对容量 2 空 1 位同时 confirm | 一个成功；一个 409 `ROOM_FULL`；`member_count==capacity`；无超员 |
| R-04 | 满员清理 | 房间 3/4，第四人加入 | 成功；status=FULL；该寝其余 open 请求 CANCELLED/FULL；相关方收到 `SYSTEM`；成员收到 `ROOM_FULL` |
| R-05 | 锁定 | 房主 lock RECRUITING | 200；LOCKED；该寝 open 请求 CANCELLED/LOCKED；成员收到 `ROOM_LOCKED`；不接受新请求 |
| R-06 | 锁定后 confirm | 锁定后第二步 | 409 `ROOM_LOCKED`；请求保持 open 或已被锁定清理（按清理时机） |
| R-07 | 解锁 | 房主 unlock LOCKED | 200；RECRUITING；不恢复已关闭请求 |
| R-08 | 非房主锁定 | 成员 lock | 403 `NOT_OWNER` |
| R-09 | 房主退出 | 房主 leave | 409 `OWNER_MUST_TRANSFER_OR_DISSOLVE` |
| R-10 | 成员退出 | 非房主 leave | 200；LEFT/LEFT；member_count-1；FULL→RECRUITING；剩余成员收到 `MEMBER_LEFT` |
| R-11 | 移除成员 | 房主 remove 非房主 | 200；REMOVED/REMOVED；member_count-1；被移除者收到 `MEMBER_LEFT` |
| R-12 | 移除房主 | 房主 remove 自己 | 409 `CANNOT_REMOVE_OWNER` |
| R-13 | 退出/移除后回原寝 | 重新申请/被邀请同一房间 | **创建时**即拒绝：`409 INVALID_STATE`（`detail.reason=REJOIN_NOT_ALLOWED`）；同房同人历史记录不可回流；可加入其他寝室 |
| R-14 | 解散 | 房主 dissolve | 200；DISSOLVED；成员全部 LEFT/DISSOLVED；member_count=0；该寝 open 请求 CANCELLED/ROOM_DISSOLVED；转让 CANCELLED；成员收到 `ROOM_DISSOLVED` |
| R-15 | 归档 | 窗口结束 cron | 房间 ARCHIVED；成员 ARCHIVED；请求 CANCELLED/ARCHIVED；转让 CANCELLED；成员收到 `ROOM_ARCHIVED`；公开链接 404 |
| R-16 | 归档成员不占名额 | 归档用户创建新请求/入新寝 | 允许；不被“一人一 ACTIVE 寝”阻塞 |
| R-17 | 已解散不再归档 | 解散后窗口结束 | 仍 DISSOLVED；不重复通知 |
| R-18 | 修改标题/标签 | 房主改 title/tags | 200；审计 `ROOM_UPDATED`；无通知；非房主 403 |
| R-19 | 修改容量 | 房主改 capacity | 409 `CAPACITY_IMMUTABLE` |
| R-20 | 公开页可见性 | 未登录访问 `/room/:code` | RECRUITING/FULL/LOCKED 返回有限字段；ARCHIVED/DISSOLVED 404；任何状态无 contact |
| R-21 | Admin 删除有成员寝室 | Admin delete | 409 `MUST_DISSOLVE_BEFORE_DELETE`；先解散后可删除/逻辑删除 |

### 13.3 RoomTransfer

| ID | 场景 | 步骤 / 断言 | 预期 |
| --- | --- | --- | --- |
| T-01 | 发起转让 | 房主 O 转让给成员 M | 200；PENDING；expires_at=+24h；M 收到 `TRANSFER_RECEIVED`；房间不变 |
| T-02 | 接受转让 | M accept | 200；ACCEPTED；O→MEMBER、M→OWNER、room.owner=M；member_count/status 不变；双方收到 `TRANSFER_ACCEPTED` |

| T-04 | 取消转让 | O cancel | 200；CANCELLED；M 收到 `TRANSFER_CANCELLED`；房主不变 |
| T-05 | 转让过期 | 改 expires_at 到过去后 accept | 409 `TRANSFER_EXPIRED`；状态 EXPIRED；角色不变 |

### 14.2 模型与迁移

| 模块 | 模型 | 本文件要求的要点 |
| --- | --- | --- |
| accounts | `User` | `gender`、`college`、`status`、`role`；性别学生不可改；逻辑删除 |
| accounts | `Profile` | 完整度=100 才可组寝；`red_lines_confirmed`（v2 新增）；JSON 字段校验 |
| accounts | `ContactInfo` | 1:1；`show_*` 开关；仅详情接口按状态返回 |
| accounts | `Block` | 双向不可见；拉黑清理在途请求 |
| connections | `ConnectionRequest` | 字段/枚举/`close_reason`（含 `BLOCKED`/`AUTO_CANCELLED`）；部分唯一索引；`expires_at` |
| rooms | `Room` | `code` 唯一 9 位；capacity 2/4/6；`member_count`；`gender/college` 快照；状态机 |
| rooms | `RoomMember` | `ARCHIVED`（v2 新增）；一人一 ACTIVE；同房同人唯一；房主唯一 |
| rooms | `RoomTransfer` | 24h；同寝唯一 PENDING；状态机 |
| adminops | `TimeWindow` | 学院唯一；无记录=关闭；不删除 |
| notifications | `Notification` | 类型/payload/read_at；与业务同事务 |
| audit | `AuditLog` | 只增不改；action/target/meta/request_id |
| adminops | `Report` | 举报只落库；Admin 人工处理 |

**迁移注意**：

- 新枚举值（`ARCHIVED`、`BLOCKED`）用 `choices` 更新，不加 DB enum（PostgreSQL 用 varchar + check 或 Django choices；按手册模型约定）。
- 部分唯一索引用 `UniqueConstraint(condition=Q(...))`；先建索引再加业务，避免上线窗口。
- `RoomMember.status` 新增 `ARCHIVED` 后，旧数据无需转换（新站从空库开始；若开发库有数据，跑一次修复命令）。
- `Profile.red_lines_confirmed` 默认 `False`；对已有“已答完”用户，数据迁移时可置 `True`（仅开发库）。
- `capacity=2` 且 `member_count=2` 的旧房间若状态为 `RECRUITING`，迁移改为 `FULL`（开发库兼容）。
- 迁移必须可回滚； destructive 变更拆两步（先加后删）。

### 14.3 服务层函数（建议签名）

```python
# services/connections.py
create_connection(actor, target_id, type, room_id=None, capacity_pref=None) -> ConnectionRequest
accept_connection(actor, connection_id) -> ConnectionRequest
decline_connection(actor, connection_id) -> ConnectionRequest
cancel_connection(actor, connection_id) -> ConnectionRequest
confirm_connection(actor, connection_id) -> ConnectionRequest
expire_due_connections(now=None, college=None, limit=500) -> int

# services/rooms.py
lock_room(actor, room_id) -> Room
unlock_room(actor, room_id) -> Room
leave_room(actor, room_id) -> RoomMember
remove_member(actor, room_id, user_id) -> RoomMember
dissolve_room(actor, room_id, reason="DISSOLVED") -> Room
archive_room(room_id, window_end, actor=None) -> Room
repair_member_count(room_id=None) -> dict

# services/transfers.py
create_transfer(actor, room_id, to_user_id) -> RoomTransfer
accept_transfer(actor, transfer_id) -> RoomTransfer
decline_transfer(actor, transfer_id) -> RoomTransfer
cancel_transfer(actor, transfer_id) -> RoomTransfer
expire_due_transfers(now=None, limit=500) -> int
```

**统一约束**：

- 每个写函数自身 `@transaction.atomic`（或在调用方 atomic 内，但必须明确边界）；入口视图不嵌套多个写事务。
- 函数开头做轻量校验（快速失败），加锁后**重新校验**；不能只信锁前对象。
- 所有错误抛 `Conflict(code, message, detail, status=409)` / `Forbidden` / `NotFound`；视图统一映射。
- 返回对象由视图序列化；service 不返回 HttpResponse。
- 通知/审计在同一事务调用；不要 `on_commit` 延迟到事务外（否则回滚后仍发通知）。
- 不在 service 里发邮件/短信；本期只有站内信。

### 14.4 API / 权限 / 错误

| 端点组 | 方法 | 权限 | 说明 |
| --- | --- | --- | --- |
| `/api/connections` | POST | 学生 | 创建三种请求；限频 |

| `/api/connections/:id/decline` | POST | 目标 | PENDING→DECLINED |

| `/api/connections/:id/confirm` | POST | 双方 | 第一步/第二步 |
| `/api/rooms` | GET | 学生 | 广场：仅本学院同性别 RECRUITING |
| `/api/rooms/:code` | GET | 公开有限/成员完整 | 公开页有限字段；无 contact |
| `/api/rooms/:id` | PATCH | 房主 | 仅 title/tags；非终态 |
| `/api/rooms/:id/lock` / `unlock` | POST | 房主 | 状态机 |

- 视图只做：解析参数 → 调 service → 序列化；不直接 `Model.objects.update()`。
- 权限类：`IsStudent`、`IsParticipant`、`IsRoomOwner`、`IsRoomMember`、`IsAdmin`；对象级权限在 service 再校验一次（防止绕过）。
- 错误处理：自定义 `exception_handler` 把 `Conflict` 等映射为 §10 格式；DRF 校验错误也统一包装。
- 分页/筛选：列表统一 `{count,next,previous,results}`；连接列表按 `updated_at DESC`；通知按 `created_at DESC`。

### 14.5 定时任务

| 任务 | 频率 | 行为 | 幂等 |
| --- | --- | --- | --- |
| `expire_connections` | 每 10 分钟 | 关闭到期 open 请求（EXPIRED/TIMEOUT） | 行锁+状态重读 |
| `archive_rooms` | 每 10 分钟 | 先过期本学院请求，再归档非终态寝室 | 终态跳过 |
| `send_window_reminders` | 每日一次 | 7/3/1 天提醒；查询去重 | user+end_at+days_left |
| `cleanup_notifications` | 每日一次 | 已读 90 天/未读 180 天 | 按时间批量 |
| `backup_db` | 每日 | `pg_dump` 保留 7–14 天（手册 §8） | 外部脚本，不在 Django 内 |
| `repair_member_counts` | 手动/可选每周 | 检测并修复漂移 | 写审计 |

- Windows 本地用 Task Scheduler 调 `manage.py` 命令，或开发期手动；生产用 cron/systemd timer。
- 任务命令必须支持 `--dry-run`（至少 repair/archive）；输出处理数量。
- 批量任务用 `select_for_update(skip_locked=True)` + 分页，避免长事务锁全表；每批 200–500。

### 14.6 Admin

- 注册所有模型；`AuditLog` 只读（无 add/change/delete）；`TimeWindow` 只允许 Admin；`Room` 状态字段只读，通过 action 调 service。
- 自定义 action：
  - 关闭请求（填原因）→ `CONNECTION_ADMIN_CLOSED`；
  - 强制解散寝室 → `ROOM_FORCE_DISSOLVED`；
  - 禁用用户 → 级联（§12.5）；
  - 归档修复（仅异常时）→ `ROOM_ARCHIVED`；
  - 成员数修复 → `ROOM_MEMBER_COUNT_REPAIRED`。
- 举报处理页：查看双方 contact 需点击“查看联系方式”，写 `ADMIN_VIEW_CONTACT`；不批量展示。
- Admin 不得直接编辑 `ConnectionRequest.status`、`Room.member_count`、`RoomMember.status`（只读或 action）；防止绕过状态机。
- Jazzmin 主题；列表筛选/搜索；导出仅审计/举报（`django-import-export`），导出写审计。
