### 1.2 浏览器与设备

- 使用干净的浏览器 profile（或隐身窗口），避免旧 cookie 导致自动登录。
- 提前准备两个窗口：窗口 A = 新注册（未登录）；窗口 B = 种子用户 `demo009@stu.edu.cn`（小算09，计算机学院、男、画像完整、无寝、QQ 已公开）。
- 两个窗口并排或使用两个标签页；切窗用 `Ctrl+Tab`，不要现场找窗口。
- 字号放大到 110%（投屏可读），但保持 1440 宽无横向滚动。
- **不要把 A 和 B 放在同一个浏览器 profile 的两个标签页里后直接互换登录**：前端 token 只在内存、refresh 用 httpOnly cookie，同一 profile 新标签会自动恢复上一个用户；用两个 profile/隐身窗口，或每次先点“退出”再登录。

## 4. 口播要点（可照读，约 600 字）

1. **问题**：同学院随机分配宿舍，冲突往往来自作息、整洁、访客边界这些“事前没说清”的事。
2. **做法**：先填一份 11 + 6 + 9 的住法问卷，再看画像接近度；匹配只覆盖同学院同性别、画像完整、还没有寝室的同学。
3. **无照片**：平台不存照片，头像只是 6 个默认图形；辨识靠昵称、年级、专业、标签和自我介绍。
4. **分数解释**：分数是画像接近度，不是“成功率”；红线冲突时封顶 59 分，但候选不会被隐藏，决定权在用户。
5. **隐私**：联系方式默认不可见，只有请求被同意后才在双方之间解锁；关闭请求立即隐藏；通知、列表、日志、审计里都不出现。
6. **两步确认**：任何组寝都要双方各确认一次；容量 2 建寝即满员，容量 4/6 建寝后进入招募。
7. **边界**：一人同时只能有一个有效寝室；重复请求、抢最后空位、同时确认都有并发保护；窗口关闭后只能改资料，不能再发起组寝。
8. **闭环与治理**：本轮已打通“邀请/申请 → 同意 → 互见 → 双方确认 → 建寝/入寝”，并支持寝室广场、转让、退出/移除、公开分享页、通知中心与时间窗；举报/拉黑与 Admin 已具备基础能力，后续继续打磨运营体验。

### 4.1 可口播的关键数字

- 11 道硬指标、6 道软指标、9 条红线、42 个标签、6 个 Prompt 题目、6 个默认头像。
- 六维权重：作息 20、整洁 20、社交 15、声音 15、边界 15、开销 15。
- 红线封顶 59；标签加成最多 6；红线扣分每条 15、最多 30。
- 请求有效期：`PENDING` 48h、`CONTACT_SHARED` 7d、`CONFIRMING` 48h；转让 24h。
- 限制：在途 ≤3、每 24h ≤10 条邀请/申请；seed 6 寝/8 请求/79 通知。

## 5. 失败回退预案

| 现象 | 可能原因 | 现场处理 |
| --- | --- | --- |
| 首页打不开 | 前端未启动/端口占用 | 切到已录屏；P1 重启 `npm run dev` |
| 注册 500/网络错误 | 后端/数据库未起 | 打开 `/api/health/` 确认；切录屏 |
| 验证码收不到 | 未接邮件服务 | 说明“开发环境固定 123456”，点“发送验证码”后看接口返回的 `dev_code` |
| 注册 409 `EMAIL_TAKEN` | 彩排残留账号 | 换 `demo042@stu.edu.cn`，或先删除残留账号 |
| 注册 400 密码相似 | 密码与邮箱相似（Django 校验） | 用 `Cohabit2026!` 这类不含邮箱前缀的强密码 |
| 邀请码 403/400 | 未填（403 `INVITE_REQUIRED`）或码错误/过期（400 `INVITE_INVALID`） | 用 `COHAB2026`；或临时关闭 `INVITE_REQUIRED`（仅本地） |
| 匹配列表空 | 画像未到 100 / 时间窗 / seed 未跑 | 先看完成度；`seed_demo --reset`；确认 A 画像 100 |
| 冲突卡 59 分不出现 | 小算10 的 `smoke` 不是 `yes` 或 A 未勾红线 | 换用 seed 中已声明的冲突对；或跳过该卡 |
| 详情底部没有“发起邀请” | 页面未加载完/后端请求失败 | 刷新详情；确认 t14 版本；回退到已录屏 |
| 邀请 429 | 24h 内请求过多（彩排反复） | `seed_demo --reset`；或换 A 账号 |
| 邀请 409 `DUPLICATE_REQUEST` | 彩排残留 open 请求 | `seed_demo --reset`；换 B 账号 |
| B 收件箱没有请求 | A/B 不同学院或性别，或请求被拒/过期 | 确认同院同性别；用 seed 的 demo009；`seed_demo --reset` |
| 同意后看不到联系方式 | B 未填联系方式/`show_*` 关闭/状态未刷新 | 用 B 账号在“我的资料 → 联系方式”填合成值并打开开关；刷新页面 |
| 发起人找不到第二步入口 | 发起人的请求不在“收到的” | 切 `/connections?role=sent`（“发出的”），点这条请求进详情 |
| 第二步 409 `ROOM_FULL` | B 在此期间进了别的寝 | 换 B；或说明“这正是容量保护在起作用” |
| 建寝后寝室页 404 | 路由用错（`/rooms/{id}` 与 `/rooms/{code}`） | 用返回的 9 位 `code` |
| 窗口关闭 409 `WINDOW_CLOSED` | seed 的窗口已过期（+7 天后） | `seed_demo --reset` 重建相对时间窗口 |
| 接口未实现 | 版本回退/静态资源旧缓存 | 确认 M4 分支；`npm run build` 后刷新；切录屏 |

## 8. 常见提问与回答（Q&A）

| 问题 | 回答要点 |
| --- | --- |
| 为什么不做照片/颜值？ | 产品目标是“讲清楚怎么住”，照片会把注意力带到不相关维度；也降低隐私与骚扰风险。头像只是区分人的几何图形。 |
| 分数怎么算？会不会不公平？ | 六维接近度加权 + 标签小加成 − 红线扣分，红线冲突封顶 59；分数只用于排序，不决定能不能邀请。公式与权重公开在 03 §8。 |
| 联系方式会不会泄漏？ | 默认不可见；只有请求被同意后、且双方开关打开时，才在**请求详情**里返回；关闭请求立即隐藏；列表/通知/审计/错误都不含联系方式。 |
| 一个人能同时占两个寝室吗？ | 不能；数据库层有“一人一个 ACTIVE 寝室”的部分唯一索引，接口层再校验。 |
| 有人抢最后一张床位怎么办？ | 入寝走行锁 + 重读空位；并发时只有一个成功，另一个 409 `ROOM_FULL`，不会超员。 |
| 两个人同时点确认会建两个寝吗？ | 不会；双方各确认一次，第二次确认在同一事务里建寝/入寝；并发用例保证只产生一个寝室。 |
| 退出后还能回原寝吗？ | 不能；对同一房间再次发起申请/邀请会 409 `REJOIN_NOT_ALLOWED`，避免“反复进出”破坏成员关系。 |
| 匹配不到人怎么办？ | 空态会说明原因（同院同性别、画像完整、无寝、未被拉黑）；可去广场看寝室，或先完善画像。 |
| 为什么列表里有人分数 59？ | 存在红线冲突（例如你声明不能接受吸烟，对方吸烟），按规则封顶；仍展示是为了让你自己判断，邀请前会二次确认。 |
| 数据是真的吗？ | 演示使用种子数据（41 人/6 寝/8 请求），联系方式为合成值；真实环境不会写入演示数据。 |
| 下一阶段做什么？ | 治理与运营深化：举报/拉黑流程打磨、Admin 审计与导出、通知偏好、移动端细节与可访问性；组寝闭环已在 M4 完成。 |

## 10. 演示禁忌

- 不打开 Django Admin、数据库客户端、Swagger（除非观众明确要求技术细节）；不展示源码。
- 不展示真实姓名、真实 QQ/微信/手机号、真实邮箱（演示邮箱为 `@stu.edu.cn` 合成账号）。
- 不点击“解散寝室”“删除账号”等破坏性动作；不现场重装依赖、不现场迁移。
- 不承诺未实现功能；接口未实现时说“下一阶段”，不即兴编造。
- 不把分数说成“匹配概率/成功率”；不说“系统保证合拍”。
