## 0. 团队环境配置（给 AI/Agent 的直接执行说明）

本节是“队友成为 GitHub 协作者并 clone 后，从零跑到可登录”的快速 checklist。人类可以照做；AI/Agent 可以把它当作可执行任务。更细的 Windows 排错见 [附录 D](#ad)。

### 0.1 给 AI 的启动提示（可直接复制）

```text
请阅读 D:\cohabit\docs\管理员使用手册.md 的第 0 节，按其中步骤帮我在本机把 Cohabit 配置到可登录。

0) 优先尝试仓库自带的一键脚本：在仓库根目录运行 `.\0.cohabit\scripts\dev.ps1 up`；只有脚本失败时才按 §0.3 的手动步骤补齐，不要跳过脚本直接重装整个环境。
1) 先检查并报告：仓库绝对路径、操作系统、Python 3.12、Node 22/24、PostgreSQL 16、8000/5173/5433 端口占用情况。
2) 缺少的路径/密码/数据库授权先问我，不要猜；不要使用生产库，不要复制别人的 .pgdata。
```

### 0.2 目标环境

| 依赖 | 目标版本 | 说明 |
| --- | --- | --- |
| Python | **3.12.x**（仓库验证 3.12.15） | 不要用 3.13+ 冒险 |
| Node.js / npm | Node **22 LTS 或 24**（仓库验证 24.22.2）；npm 10/11 | Vite 7 需要较新的 Node |
| PostgreSQL | **16.x** | 安装版或 `D:\tools\pgsql16` 便携版均可 |

不需要 Redis、Celery、Docker；定时维护用 Django management command。

### 0.3 最小执行路径（Windows PowerShell）

#### 一键脚本（优先）

仓库自带 `0.cohabit/scripts/dev.ps1`，用于把“检查环境 → 准备 `.env` → 建 venv/装依赖 → 本地 PostgreSQL 建库 → migrate → seed → 启动 8000/5173”串成一条命令。脚本不会安装 Python、Node 或 PostgreSQL，也不会改业务代码或自动提交 Git。

```powershell
cd D:\cohabit

# 首次或日常：准备 + 启动
.\0.cohabit\scripts\dev.ps1 up

# 也可以分步执行
.\0.cohabit\scripts\dev.ps1 setup
.\0.cohabit\scripts\dev.ps1 start
.\0.cohabit\scripts\dev.ps1 status
.\0.cohabit\scripts\dev.ps1 stop
```

| 命令 | 用途 |
| --- | --- |
| `up` | 等于 `setup` + `start`；第一次配置和日常启动都可以用 |
| `setup` | 检查/生成 `backend/.env` 和 `frontend/.env.local`、建 venv/装 Python 依赖、`npm ci`、检查/启动本地 PostgreSQL、建 `cohabit` 角色与 `cohabit_dev` 库、`migrate`、空库时 `seed_demo`、`manage.py check` |
| `start` | 确保 PostgreSQL/数据库可用，启动 Django `127.0.0.1:8000` 和 Vite `127.0.0.1:5173`，等待健康检查并打印入口、账号、日志路径 |
| `status` | 检查 PostgreSQL 5433、后端 8000、前端 5173 和健康检查 |
| `stop` | 只停止本脚本记录的进程；不会误停其他终端启动的服务 |
| `stop -Postgres` | 在 `stop` 基础上停止脚本用 `D:\cohabit\0.cohabit\.pgdata` 启动的 PostgreSQL |
| `reset -Force` | 对**本地开发库**执行 `seed_demo --reset`；会清空并重建演示数据，不要在共享库/生产库使用 |

> **编码注意（2026-11-26）**：`dev.ps1` 含中文，文件必须保存为 **UTF-8 with BOM**。Windows PowerShell 5.1 会按系统 ANSI 代码页（简体中文为 GBK）读取无 BOM 的 UTF-8 脚本，导致中文字符串被错误解码，典型报错是 `Unexpected token '}'`（常见于第 208 行附近）。如果从旧提交/旧压缩包拿到脚本后出现该报错：改用 PowerShell 7（`pwsh`）运行，或在编辑器中把 `dev.ps1` 另存为“UTF-8 with BOM”；也可以跳过脚本，直接按下面的手动步骤启动。

脚本的行为与边界：

- 工作目录必须能从脚本位置推导到仓库根；默认数据目录是 `0.cohabit/.pgdata`，端口默认 5433，读取 `backend/.env` 的 `DATABASE_URL`。
- PostgreSQL 可执行文件依次查找 `$env:PG_BIN`、`D:\tools\pgsql16\bin`、`C:\Program Files\PostgreSQL\16\bin` 和 PATH；找不到时按 §0 前面的依赖表安装。
- 首次运行会从 `.env.example` 生成 `backend/.env` 和 `frontend/.env.local`，并生成随机 `SECRET_KEY`；这两个文件都不要提交。
- 空库才自动 seed；已有用户时跳过。需要重置演示数据时显式执行 `reset -Force`，并确认目标是本地开发库。
- 日志和 PID 文件在 `0.cohabit/.walkthrough/dev/`，不进入 Git；`stop` 只管理脚本启动的进程。
- 如果 8000/5173 已被其他进程占用，脚本会复用/报告占用，不会强行杀掉；先确认占用者是不是你自己的服务。
- 脚本失败时不要反复重装；按下面“手动步骤”逐步定位，或把失败命令和错误行发给维护者。

#### 手动步骤（脚本失败时）

以下 `<REPO_DIR>` 表示仓库根目录，示例为 `D:\cohabit`；其他路径请整体替换。

#### 第 1 步：clone 与确认文件

```powershell
git clone https://github.com/linkkkss/cohabit.git D:\cohabit
cd D:\cohabit
Test-Path 0.cohabit\backend\.env.example
Test-Path 0.cohabit\frontend\.env.example
```

仓库**不会**带以下内容，必须本地生成：

- `0.cohabit/backend/.env`
- `0.cohabit/frontend/.env.local`
- `.venv`、`node_modules`
- `.pgdata`、`.pgpw`、数据库角色/库
- seed 演示数据

#### 第 2 步：后端虚拟环境与 `.env`

```powershell
cd D:\cohabit\0.cohabit\backend
Copy-Item .env.example .env

# 有 uv：
uv venv --python 3.12 .venv
uv pip install -r requirements\dev.txt

# 没有 uv：
# py -3.12 -m venv .venv
# .\.venv\Scripts\python.exe -m pip install -r requirements\dev.txt
```

生成 `SECRET_KEY`：

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(50))"
```

把结果写进 `.env` 的 `SECRET_KEY=`，并确认：

```dotenv
DJANGO_SETTINGS_MODULE=config.settings.dev
DEBUG=true
DATABASE_URL=postgres://cohabit:cohabit_dev_pw@127.0.0.1:5433/cohabit_dev
INVITE_REQUIRED=false
DEV_VERIFICATION_CODE=123456
```

#### 第 3 步：本地 PostgreSQL

先确认本机是否已有 PostgreSQL 16：

```powershell
Get-Service *postgres*
Get-Process postgres -ErrorAction SilentlyContinue
Test-Path D:\tools\pgsql16\bin\pg_ctl.exe
```

**情况 A：使用仓库默认的 5433 便携版**

```powershell
# 仅在 .pgdata 不存在/为空时执行；不要覆盖已有数据目录
D:\tools\pgsql16\bin\initdb.exe -D D:\cohabit\0.cohabit\.pgdata -U postgres --encoding=UTF8 --locale=C

# 启动（端口必须与 .env 一致）
D:\tools\pgsql16\bin\pg_ctl.exe -D D:\cohabit\0.cohabit\.pgdata -o "-p 5433" start

# 首次建角色/库；已存在则跳过或改用 ALTER ROLE
D:\tools\pgsql16\bin\psql.exe -p 5433 -U postgres -c "CREATE ROLE cohabit LOGIN PASSWORD 'cohabit_dev_pw';"
D:\tools\pgsql16\bin\psql.exe -p 5433 -U postgres -c "CREATE DATABASE cohabit_dev OWNER cohabit;"
```

**情况 B：本机已有 PostgreSQL 16 在 5432**

用 pgAdmin 或 psql 建同样的角色/库，然后把 `.env` 改为：

```dotenv
DATABASE_URL=postgres://cohabit:cohabit_dev_pw@127.0.0.1:5432/cohabit_dev
```

> **不要复制别人的 `.pgdata`。** 数据目录与操作系统、PostgreSQL 版本、端口强绑定；重新 `initdb` + `migrate` + `seed_demo` 最稳。也不要为了“省事”去改已有业务库；先确认它是本地开发库。

#### 第 4 步：迁移与 seed

```powershell
cd D:\cohabit\0.cohabit\backend
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py seed_demo --reset
.\.venv\Scripts\python.exe manage.py check
```

`seed_demo --reset` 会重建演示数据，**只对本地开发库执行**；它会创建 41 用户/40 画像/40 联系方式/6 寝/20 成员/8 请求/2 转让/79 通知/2 时间窗/1 邀请码/2 举报/4 拉黑/10 审计。

#### 第 5 步：前端依赖与 `.env.local`

```powershell
cd D:\cohabit\0.cohabit\frontend
Copy-Item .env.example .env.local
npm ci
```

默认保持：

```dotenv
VITE_API_BASE_URL=
VITE_ALLOW_PREVIEW=true
```

`VITE_API_BASE_URL` 留空走 Vite `/api` 代理；**不要**随手填 `http://127.0.0.1:8000`，否则可能跨域。

#### 第 6 步：启动并验收

```powershell
# 终端 A
cd D:\cohabit\0.cohabit\backend
.\.venv\Scripts\python.exe manage.py runserver 8000

# 终端 B
cd D:\cohabit\0.cohabit\frontend
npm run dev
```

| 验收项 | 期望 |
| --- | --- |
| <http://127.0.0.1:8000/api/health/> | `{status:"ok", db:"ok"}`，200 |
| <http://127.0.0.1:8000/admin/> | 200，可登录 |
| <http://127.0.0.1:5173/> | 200，标题 `Cohabit · 校园舍友匹配` |
| 学生登录 | `demo009@stu.edu.cn` / `Demo1234!` |
| 管理员登录 | `admin@cohabit.local` / `Admin1234!` |
| 邀请码 | `COHAB2026` |
| 本地验证码 | `123456` |

可选：`npm run build`（当前基线 270 modules）和 `pytest -q`（当前基线 730 passed），用于确认环境完整。

### 0.4 必须修改/确认的配置

| 文件 | 配置 | 说明 |
| --- | --- | --- |
| `backend/.env` | `SECRET_KEY` | 每台机器独立；不要提交 |

| `frontend/.env.local` | `VITE_ALLOW_PREVIEW=true` | 仅预览用；真实构建可关 |

默认端口：**后端 8000 / 前端 5173 / 数据库 5433**。端口被占用时不要静默 kill 进程，先报告；改端口时需同步 `.env`、`vite.config.ts` 或启动命令。

- **禁止**自动 commit/push/tag；Git 由用户手动操作。

## 1. 开始之前

### 1.1 管理入口与账号

- 管理后台地址：`/admin/`；本地开发入口、端口和启动命令见 [§0](#a0) 或 [附录 D](#ad)。
- 本地演示管理员：`admin@cohabit.local` / `Admin1234!`，UID `0000000099`。
- 正式环境请使用学校分配的管理员账号，并在首次登录后修改密码。
- 只有 `is_staff=True` 的账号可以进入后台；`is_superuser=True` 拥有全部模型权限。普通学生账号不能进入。

### 1.2 权限模型

后台权限按 Django 的“模型 + 动作”控制：

- **查看**：能打开列表和详情；
- **修改**：能编辑字段、执行依赖修改权限的动作；
- **删除**：能删除对象（部分模型明确禁止）；
- **导出的 CSV**：属于动作，但仍受对应模型权限约束。

如果某个菜单或动作看不到，先检查账号的 staff 状态和模型权限，不要用超级用户账号日常操作。

### 1.3 三条硬规则

1. **不要用管理员身份代替学生确认组寝。** 后台没有 accept/confirm 一类动作（S-06）；需要推进流程时，让学生本人在页面上操作。
2. **不要批量导出联系方式。** 用户、画像、寝室、请求、通知、举报、审计的 CSV 都不包含 QQ、微信、手机号；举报详情页的“查看目标联系方式”必须逐次查看并写审计。
3. **不要直接改数据库。** 状态变更应通过后台动作或维护命令完成，保证审计、通知和成员计数一致。

## 2. 管理后台总览

登录后，后台首页按应用分组展示可管理的模型。常用分组如下：

| 分组 | 主要模型 | 用途 |
| --- | --- | --- |
| 账号 | 用户、邀请码、联系方式 | 账号状态、邀请码、联系方式只读检查 |
| 画像 | 画像 | 只读查看问卷与完成度 |
| 寝室 | 寝室、寝室成员、房主转让 | 查看、强制解散、导出 |
| 组寝 | 组寝请求 | 查看、导出；不代替学生确认 |
| 通知 | 站内通知 | 查看、筛选、导出 |
| 运营 | 时间窗、举报、拉黑、审计日志 | 时间窗、举报处理、审计 |

### 2.1 列表页通用操作

- 顶部搜索框：按 UID、邮箱、昵称、编号等搜索（各模型支持字段不同）。
- 右侧筛选器：按状态、类型、日期等过滤。
- 勾选行前的复选框，再选择“动作”下拉框中的批量动作。
- 日期层级（date hierarchy）可按年/月/日快速缩小范围。
- 导出动作会下载带 BOM 的 UTF-8 CSV，Excel 打开中文一般不会乱码。

### 2.2 详情页通用注意

- 只读字段会显示为灰色，不能直接编辑。
- 部分模型禁止新增或删除，按钮不会出现。
- 所有导出动作都会写一条 `AUDIT_EXPORTED` 审计；请勿频繁重复导出。
- 页面上看不到某个动作，通常是因为当前对象状态不允许，或账号缺少权限。

<a id="a3"></a>
## 3. 用户管理

路径：`账号 → 用户`。

### 3.1 查看与筛选

- 搜索：UID、邮箱、昵称、学院、专业。
- 筛选：角色、状态、性别、学院、是否 staff、是否启用。
- 列表列：UID、邮箱、昵称、角色、状态、学院、性别、年级、staff、启用状态、创建时间。
- 详情页可查看基础资料、角色与状态、权限组、登录时间等。

### 3.2 禁用账号（级联清理）

选中用户，执行 **“禁用所选用户（级联清理在途请求/寝室）”**。

该动作会：

- 将账号置为停用/禁用，之后不能登录；
- 关闭该用户所有进行中的组寝请求，关闭原因为 `USER_DISABLED`；
- 如果该用户是房主，强制解散其寝室，成员离开；
- 如果该用户是普通成员，将其标记为离开；
- 取消与该用户相关的待处理房主转让；
- 清空联系方式；
- 写入 `USER_DISABLED` 审计。

注意事项：

- 当前登录账号会被跳过，不能禁用自己；
- 已禁用账号会跳过；
- 批量执行时逐条处理，单条失败会提示，不影响其他用户；
- 禁用没有“一键恢复”动作。确需恢复时，先评估原因，再按运维流程处理，不要直接改库。

### 3.3 导出用户

执行 **“导出所选用户 CSV（不含邮箱/密码/联系方式）”**。

导出列：

```text
uid, nickname, gender, grade, college, major, role, status,
is_staff, is_active, created_at
```

不包含：邮箱、密码、QQ、微信、手机号、token。导出动作会写 `AUDIT_EXPORTED`。

### 3.4 联系方式（只读）

路径：`账号 → 联系方式`。

- 列表只显示“已填 QQ / 已填微信 / 已填手机”的布尔标记；
- 详情页的联系方式字段为只读，**不展开明文**；
- 不提供批量导出；
- 如因举报处理确需查看，请走“举报 → 查看目标联系方式”，每次都会写审计。

### 3.5 新增用户

后台可以新增用户，字段包括邮箱、昵称、性别、年级、学院、专业、角色、状态、staff、启用状态和密码。UID 由服务端生成。

通常不建议在后台手工创建学生账号；正式环境优先使用注册流程，演示环境优先使用 `seed_demo`。

## 6. 寝室、成员与房主转让

### 6.1 寝室列表

路径：`寝室 → 寝室`。

- 搜索：编号、标题、房主 UID/昵称、学院、专业。
- 筛选：状态、容量、性别、学院、创建日期。
- 列表列：编号、标题、房主、容量、当前人数、性别、学院、状态、创建时间。
- 详情页：查看成员、标签、时间；`member_count` 为只读，由服务层维护。

### 6.2 强制解散

选中寝室，执行 **“强制解散所选寝室（写 ROOM_FORCE_DISSOLVED 审计）”**。

- 复用服务层 `dissolve_room(force=True, reason="ADMIN_FORCE")`；
- 所有成员离开，寝室状态变为 `DISSOLVED`；
- 编号失效，公开链接 404；
- 写入 `ROOM_FORCE_DISSOLVED` 审计；
- 操作不可撤销，执行前请确认不是误操作。

### 6.3 删除保护（R-21）

有 **ACTIVE 成员**的寝室不能直接删除：

- `has_delete_permission` 返回 `False`，详情页不显示删除按钮；
- 如果通过批量删除尝试，`delete_model`/`delete_queryset` 会提示 `MUST_DISSOLVE_BEFORE_DELETE`，并跳过该寝室；
- 正确做法：先强制解散，再按需删除历史记录；
- 打开详情页时不会弹“请先解散”的错误提示，提示只在实际删除时出现。

### 6.4 导出寝室

动作：**“导出所选寝室 CSV（不含联系方式）”**。

导出列：

```text
code, title, owner_uid, capacity, member_count,
gender, college, major, status, created_at
```

### 6.5 寝室成员

路径：`寝室 → 寝室成员`。

- 筛选：角色、状态、原因、创建日期。
- 可查看成员与寝室的对应关系、加入/离开时间、离开原因。
- 导出动作：**“导出所选寝室成员 CSV（不含联系方式）”**。
- 导出列：

```text
id, room_code, user_uid, role, status, reason, left_at, created_at
```

不要手工修改成员状态；成员变更应通过学生端动作、房主移除或禁用级联完成。

### 6.6 房主转让

路径：`寝室 → 房主转让`。

- 筛选：状态、创建日期。
- 可查看发起人、目标成员、状态、过期时间、决定时间。
- 转让有效期为 24 小时；由学生在页面上接受、拒绝或撤销。
- 管理员不提供“直接改成房主”的动作；如需处理异常，先联系双方并按运维流程评估。

## 9. 时间窗管理

路径：`运营 → 时间窗`。

### 9.1 规则

- 每个学院一条时间窗，`college` 唯一；
- `start_at` 必须早于 `end_at`；
- 不支持删除，只能新建或修改时间；
- 时间窗只限制组寝写操作，不影响注册/登录/资料/问卷/举报/拉黑/已读；
- 管理员和定时任务不受时间窗拦截，但相关操作仍应留下审计。

### 9.2 修改时间窗

- 打开时间窗详情，修改开始/结束时间后保存；
- 延长结束时间可以继续开放（如果原来未归档）；
- 已归档的寝室不会因为延长窗口自动复活；
- 提前结束会影响写操作，但不会自动删除已有寝室；
- 修改后，学生端时间窗横幅会按新时间显示。

### 9.3 学生端状态接口

学生端通过 `GET /api/timewindow/` 获取状态：

```json
{
  "college": "计算机学院",
  "status": "OPEN",
  "is_open": true,
  "start_at": "2026-11-10T00:00:00+08:00",
  "end_at": "2026-11-20T23:59:59+08:00",
  "days_until_start": 0,
  "days_until_end": 5,
  "server_time": "2026-11-15T12:00:00+08:00"
}
```

`status` 为 `OPEN` / `UPCOMING` / `CLOSED`。无记录、无学院或已结束通常返回 `CLOSED`。

## 10. 举报处理与联系方式查看

路径：`运营 → 举报`。

### 10.1 查看举报

- 筛选：状态、对象类型、创建日期。
- 搜索：举报人 UID/昵称、原因。
- 列表列：ID、举报人、对象类型、对象 ID、状态、处理人、创建时间。
- 列表**不显示**联系方式明文。

举报对象类型：

- `USER`：目标用户；
- `ROOM`：目标寝室（联系方式取房主）；
- `CONNECTION`：目标组寝请求（取双方）。

### 10.2 处理举报

选中 OPEN 状态的举报，执行：

- **“标记为已处理”**（`mark_resolved`）；
- **“标记为驳回”**（`mark_dismissed`）。

处理逻辑：

- 逐条使用独立事务和行锁；
- 只处理仍为 OPEN 的记录；已处理的会跳过；
- 状态、`REPORT_HANDLED` 审计、举报人通知同事务提交；
- 单条失败会回滚该条并提示，继续处理其余；
- 处理结果会通知举报人，不通知被举报人。

后台没有“直接封禁被举报人”的动作。是否禁用账号，需要另行走用户管理的 `disable_users`，并确认理由与证据。

### 10.3 查看目标联系方式（逐次审计）

在举报详情页点击 **“查看目标联系方式（写审计）”**：

- 需要该举报的 `change` 权限；没有权限会 403；
- 权限校验发生在读取联系方式之前，失败不会写 `ADMIN_VIEW_CONTACT`；
- 每查看一个目标用户，写一条 `ADMIN_VIEW_CONTACT` 审计；
- 审计 meta 只记录 `target_user_id` 和 `report_id`，不记录联系方式值；
- 页面不缓存（`Cache-Control: no-store`）；
- 不提供批量查看，不提供联系方式 CSV 导出。

只查看处理当前举报所必需的信息，不要截图、复制或外传。

### 10.4 导出举报

动作：**“导出所选举报 CSV（不含邮箱/联系方式）”**。

导出列：

```text
id, target_type, target_id, status, reporter_uid,
handled_by_uid, reason, created_at
```

## 13. 定时维护命令

以下命令在 `0.cohabit/backend` 下执行。Windows 示例使用虚拟环境 Python：

```powershell
cd D:\cohabit\0.cohabit\backend
.\.venv\Scripts\python.exe manage.py <命令> [--dry-run]
```

### 13.1 命令清单

| 命令 | 作用 | 建议频率 |
| --- | --- | --- |
| `expire_connections` | 关闭到期的 open 请求 | 每 10 分钟 |
| `archive_rooms` | 归档结束时间窗的寝室，先过期在途请求 | 每 10 分钟，且在 `expire_connections` 之后 |
| `expire_transfers` | 关闭 24 小时未处理的房主转让 | 每 10 分钟 |
| `send_window_reminders` | 发送 7/3/1 天窗口关闭提醒 | 每天至少一次 |
| `cleanup_notifications` | 清理已读 90 天/未读 180 天通知 | 每天一次 |
| `repair_member_count` | 修复单个寝室人数计数 | 按需 |
| `repair_member_counts` | 批量检查/修复人数计数 | 每周或异常后 |

### 13.2 执行顺序

窗口结束时建议顺序：

```text
1. expire_connections
2. archive_rooms
3. expire_transfers
4. send_window_reminders
5. cleanup_notifications
```

`archive_rooms` 内部也会先处理该学院的到期请求，但显式先跑 `expire_connections` 更便于排查。

### 13.3 dry-run 与幂等

- 多数命令支持 `--dry-run`，只统计不写库；首次执行或排查时先用它。
- 命令可重复执行；第二次通常返回 0 变更（`skipped` 表示已处理）。
- `archive_rooms` 只处理非终态寝室；`ARCHIVED` 保留归档快照，`DISSOLVED` 跳过。
- `repair_member_count(s)` 只统计非终态寝室；不会把归档寝室的 6/6 快照改成 0/6。

### 13.4 提醒与清理

- 提醒在结束前 7/3/1 天各发一次；
- 去重键为“用户 + 结束时间 + 剩余天数”，重复执行不会重复发；
- 已读通知保留 90 天，未读 180 天；
- 审计日志不受通知清理影响。

### 13.5 cron 示例

```cron
*/10 * * * * cd /srv/cohabit/backend && .venv/bin/python manage.py expire_connections
*/10 * * * * cd /srv/cohabit/backend && .venv/bin/python manage.py archive_rooms
*/10 * * * * cd /srv/cohabit/backend && .venv/bin/python manage.py expire_transfers
15 3 * * *   cd /srv/cohabit/backend && .venv/bin/python manage.py send_window_reminders
30 3 * * *   cd /srv/cohabit/backend && .venv/bin/python manage.py cleanup_notifications
0 4 * * 1    cd /srv/cohabit/backend && .venv/bin/python manage.py repair_member_counts
```

请根据服务器时区调整；`archive_rooms` 的判断使用服务端时间，不依赖 cron 时区。

## 15. 安全、隐私与合规

### 15.1 最小必要

- 只在处理具体举报/故障时查看联系方式；
- 不批量浏览、不导出、不截图联系方式；
- 不把后台账号借给他人；
- 不在公共电脑保存后台登录状态。

### 15.2 导出安全

- 所有 CSV 都不包含邮箱、密码、QQ、微信、手机号、token；
- 导出动作写 `AUDIT_EXPORTED`，能追溯“谁在什么时候导出了什么”；
- CSV 含 BOM，便于 Excel 打开，但也更容易被转发；请按学校数据制度存放和销毁。

### 15.3 审计

- 不要尝试修改或删除 `AuditLog`；后台本身也只读；
- 举报处理、禁用账号、强制解散、查看联系方式、导出都有审计；
- 审计日志是纠纷处理和安全事件调查的依据。

### 15.4 账号与权限

- 离职/换岗后及时回收 staff 权限；
- 定期检查 `is_staff`、`is_superuser` 列表；
- 不要给学生账号授予 staff；
- 发现异常登录或批量导出，先停用账号并保留审计。

### 15.5 事件处理建议

1. 先保护当事人：必要时拉黑/停用账号；
2. 保留证据：举报内容、请求记录、审计日志；
3. 按学校流程联系当事人，不在公开渠道披露隐私；
4. 处理完成后记录结论，必要时补充审计说明。

## 16. 常见问题

**Q1：登录 `/admin/` 一直 403 或 CSRF 失败？**  
本地开发经 Vite 代理（5173/5174/4173）访问时，需要后端 dev 配置信任这些 Origin；当前版本已默认配置。仍失败时，直接访问后端 `http://127.0.0.1:8000/admin/` 登录，或重启后端后重试。

**Q2：为什么不能删除有成员的寝室？**  
这是 R-21 保护。先执行“强制解散”，再删除历史记录；直接删除会提示 `MUST_DISSOLVE_BEFORE_DELETE`。

**Q3：为什么举报详情页没有“查看联系方式”或点击后 403？**  
该链接要求当前账号有该举报的 `change` 权限；没有权限不会读取联系方式，也不会写审计。请让有权限的运营人员处理。

**Q4：为什么后台不能帮学生确认组寝？**  
S-06 规定管理员不能代替学生 accept/confirm。请让学生本人在组寝请求页面操作。

**Q5：时间窗关闭后，学生还能改资料吗？**  
可以。时间窗只限制组寝写操作；资料、问卷、举报、拉黑、通知已读不受影响。

**Q6：`seed_demo --reset` 提示需要 `--force`？**  
当前 `DEBUG=False`，命令要求显式确认；确认不是生产库后加 `--force`。`ENV=production` 时仍会拒绝。

**Q7：人数计数不一致怎么办？**  
先跑 `repair_member_counts --dry-run` 查看差异，再跑实际修复。该命令只处理非终态寝室，不会改归档快照。

**Q8：导出 CSV 里为什么没有邮箱/联系方式？**  
这是刻意的隐私设计。需要联系目标时，走举报详情页的逐次查看；不要尝试从其他表拼接联系方式。

**Q9：通知/请求过期了还能恢复吗？**  
不能。过期是终态；需要重新发起。不要通过改状态字段“复活”请求。

**Q10：管理员能直接改寝室人数或成员吗？**  
不建议。成员关系应通过学生端动作或禁用级联维护；`member_count` 由服务层维护，异常时用修复命令。

### D.6 常见启动问题

**Q1：学生端能打开，但登录/匹配报网络错误。**  
先看 `http://127.0.0.1:8000/api/health/` 是否 200 且 `db:"ok"`；如果 503，检查 PostgreSQL 是否在 5433 启动。

**Q2：`/api/health/` 返回 `db:"error"`。**  
常见原因是数据库没启动，或启动到了 5432。确认 `backend/.env` 的 `DATABASE_URL` 是 `127.0.0.1:5433`，并用 D.2 的命令指定 `-p 5433`。

**Q3：从 5173 进 `/admin/` 提示 CSRF 失败。**  
直接使用 `http://127.0.0.1:8000/admin/`；或重启后端让 dev 配置生效。清一次站点 Cookie 后再试，不要在生产配置里关闭 CSRF。

**Q4：端口被占用。**  
```powershell
Get-NetTCPConnection -LocalPort 5173,8000 -State Listen |
  Select-Object LocalPort,OwningProcess
```
确认进程归属后再处理；前端可临时换 5174，后端换端口时记得同步 Vite 代理配置。

**Q5：`seed_demo --reset` 被拒绝。**  
`DEBUG=False` 时需要加 `--force`；`ENV=production` 仍会拒绝。不要在共享演示库或生产库上试。额外 ADMIN 账号不会再导致 reset 失败，且会被保留。

**Q6：多人同时跑测试时出现 `test_cohabit_dev` 不存在/被占用。**  
并行 pytest 会争用同一个测试库。各自用独立的 `DATABASE_URL` 测试库名，例如：

```powershell
$env:DATABASE_URL='postgres://cohabit:cohabit_dev_pw@127.0.0.1:5433/cohabit_m6fix_qa'
.\.venv\Scripts\python.exe -m pytest -q
```

**Q7：`dev.ps1` 报 `Unexpected token '}'`（约第 208 行）或中文乱码。**

脚本是含中文的 UTF-8 文件，但 Windows PowerShell 5.1 在简体中文系统上会按 GBK 读取无 BOM 的 UTF-8 脚本，导致字符串解码错误、语法解析失败。处理方式（任选其一）：

1. 改用 PowerShell 7 运行：`pwsh -File .\0.cohabit\scripts\dev.ps1 status`；
2. 用编辑器把 `dev.ps1` 另存为 **UTF-8 with BOM** 后重试；
3. 跳过脚本，按附录 D.2 手动启动三个进程。

当前仓库中的 `dev.ps1` 已是 UTF-8 with BOM；如果用的是旧提交或旧压缩包，仍可能遇到该问题。
