## 1. 项目定位与边界

### 1.1 一句话

**Cohabit 帮同学院同学在组寝前把作息、整洁、社交边界等讲清楚，用画像匹配 + 双向确认找到合拍的室友，而不是随机分配。**

### 1.2 目标用户与场景

- 同学院本科生（大一大二为主），在"组寝/搬寝"窗口期寻找室友；
- 用户不愿公开真实姓名/联系方式，但愿意用画像与标签表达生活习惯；
- 需要"先了解、再确认"的安全流程：联系方式只在双方第一步同意后互见；
- 管理员需要开窗、看数据、处理举报、导出成寝名单。

### 1.3 本期范围（P0）

1. 注册/登录（校园邮箱 + 验证码 + 邀请码；HttpOnly refresh）；
2. 基本资料 + 画像问卷 + 六维结果 + 完整度；
3. 匹配列表/详情（同院同性别、契合度、推荐理由、红线警示）；
4. 组寝请求：人-人邀请、房主定向邀请、入寝申请；
5. 两步确认 + 联系方式解锁 + 自动取消其余在途；
6. 寝室：创建（2/4/6）、广场、详情、申请审批、锁定/解锁、退出、移除、解散、转让；
7. 通知中心 + 未读轮询 + 通知矩阵；
8. 举报/拉黑；时间窗；Django Admin（用户/寝室/请求/举报/窗口/导出/看板可选）；
9. 种子数据 + 演示账号 + 本地一键启动。

### 1.4 明确不做（本期）

- 实时聊天/WebSocket、邮件/短信、用户照片上传与审核、复杂 RBAC、多校区、小程序、AI 解析、花哨动画、自定义 Vue 管理后台；
- **不做旧站迁移**：不导入旧账号/旧数据、不沿用旧 UI；只做新站；
- **不做真实宿舍分配**：本系统只完成"组寝关系"，不接教务/宿管系统，不生成床位；
- 不做跨学院匹配；不做跨性别组寝；
- 不做真实邮件发送（开发期固定码；上线前另议）。

### 1.5 隐私与安全红线

1. **不采集真实姓名**；昵称 + UID 即身份；
2. 联系方式存 `ContactInfo` 独立表，**任何列表接口都不返回**；
3. 联系方式只在 `CONTACT_SHARED`（及之后状态）对**请求双方**可见，遵守 `show_qq/show_wechat/show_phone`；
4. UID 搜索/画像查看限同学院同性别；跨院/跨性别返回 404，避免信息探测；
5. 所有写操作在 service 层做对象级权限 + 状态 + 窗口校验，前端隐藏按钮不算权限；
6. 日志、错误详情、审计中不得出现 token、密码、联系方式原文。

### 1.6 术语

| 术语 | 含义 |
| --- | --- |
| 画像 / Profile | 问卷答案 + 六维分 + 标签 + 红线 + prompt 回答 + 完整度 |
| 六维 | 作息、整洁、社交、噪音、边界、消费六个 0–100 分维度 |
| 红线 | 用户明确不能接受的生活习惯项；命中时降分 + 警示 |
| 词条 / 标签 | 生活化标签（如"猫派""夜猫子"），用于展示与轻量加权 |
| prompt | 2–3 个开放式问答，作为匹配列表/详情的大标题素材 |
| 组寝请求 / Connection | 邀请或申请的统一状态机对象（`ConnectionRequest`） |
| 两步确认 | 第一步同意（联系方式互见）→ 线下沟通 → 第二步双方确认（组寝成立） |
| 寝室 / Room | 组寝关系容器（非真实宿舍），9 位编号，2/4/6 人 |
| 时间窗 / TimeWindow | 按学院开放的匹配时段；未配置 = 关闭 |
| 归档 | 窗口结束时寝室转为只读历史状态 |

## 2. 角色与核心流程

### 2.1 角色

| 角色 | 认证 | 能力 |
| --- | --- | --- |
| 访客 | 无 | 营销首页、规则、隐私、登录/注册、公开寝室分享页（有限字段） |
| 学生 | access（内存）+ refresh（HttpOnly Cookie） | 资料/问卷/匹配/请求/寝室/通知/举报/拉黑/设置 |
| 管理员 | Django Session（`is_staff`） | `/admin/` 全量管理、开窗、禁用、强制解散、关闭请求、导出 |

### 2.2 主流程

1. 注册（邮箱验证码 + 可选邀请码）→ 登录；
2. 填基本资料（昵称/性别/年级/学院/专业）→ 问卷（硬指标 → 软指标 → 红线 → 词条 → prompt）→ 画像结果；
3. 匹配列表（同院同性别）→ 候选详情（六维/标签/契合度/推荐理由/红线警示）；
4. 发起组寝：人-人邀请、房主定向邀请、或申请入寝；
5. 对方**同意**（第一步）→ 状态 `CONTACT_SHARED`，双方联系方式互见；线下沟通；
6. 任一方**确认组寝**（第二步）→ `CONFIRMING`；另一方再确认 → `CONFIRMED`；
7. 事务内入寝/建寝：更新寝室成员/状态；自动取消双方其余在途请求；双方通知；
8. 寝室管理：锁定/解锁、退出、移除、解散、转让；
9. 窗口结束：在途请求过期、寝室归档，只读展示。

### 2.3 两步确认时序

```text
A（发起方）                                       B（接收方）
    |---- 发起邀请/申请 ----------------------------->|
    |                                                |
    |<--- 同意（第一步）------------------------------|   PENDING → CONTACT_SHARED
    |        双方联系方式互见（按 show_* 字段）        |   expires_at = +7d
    |        线下沟通（QQ/微信/电话）                  |
    |                                                |
    |---- 确认组寝（第二步，任一方先点）-------------->|   CONTACT_SHARED → CONFIRMING
    |<--- 确认组寝（第二步，另一方）------------------|   CONFIRMING → CONFIRMED
    |                                                |
    |==== 事务：入寝/建寝 + 自动取消其余在途 + 通知 ===|
```

**约束**：

- 第一步只能由**接收方**（`target`）同意；拒绝/超时同样由接收方或定时任务触发；
- 第二步双方各确认一次，**同一方不能重复确认**；先确认方不能替对方确认；
- 第二步任一动作在事务内 `SELECT ... FOR UPDATE` 锁请求行；双方同时点击时，后到者读到已确认时间戳并完成最终确认（不是重复确认）；
- `CONFIRMED` 时若目标寝室已满/锁定/解散/归档，则**回滚且不改变状态**，返回 `409 ROOM_FULL / INVALID_STATE`；双方仍可撤回，或等过期。

### 2.4 三种组寝入口（v2 定稿）

| 类型 | 发起人 | 目标 | `room` | 容量 | 确认后 |
| --- | --- | --- | --- | --- | --- |
| `INVITE`（人-人） | 无 ACTIVE 寝室的用户 | 无 ACTIVE 寝室的用户 | `null` | `capacity_pref` ∈ {2,4,6}，默认 4 | 新建寝室：发起人为房主，目标为成员 |
| `INVITE`（房主定向） | 寝室 `OWNER` | 无 ACTIVE 寝室的用户 | 自己的寝室 | 沿用寝室容量 | 目标加入该寝室 |
| `APPLY`（申请入寝） | 无 ACTIVE 寝室的用户 | 目标寝室 `OWNER` | 目标寝室 | 沿用寝室容量 | 申请人加入该寝室 |

共同守卫（创建时校验，确认时再校验一次）：

1. **同学院**：`initiator.college == target.college == room.college`；
2. **同性别**：`initiator.gender == target.gender == room.gender`；
3. **画像完整**：`profile.completeness == 100` 且硬/软指标齐全；
4. **无在途冲突**：同一对用户（双向）只能有一个在途请求；同一人对同一房间只能有一个在途申请；房主对同一目标在同一房间只能有一个在途邀请；
5. **无在途寝室**：发起人与目标都不能已有 `ACTIVE` 寝室（房主定向邀请时发起人除外）；
6. **未拉黑**：双向任一拉黑则 403 `BLOCKED`；
7. **窗口开放**：发起/同意/确认都必须窗口开放；
8. **寝室状态**：`RECRUITING` 且有空位；锁定/满员/归档/解散不可申请/邀请。

### 2.5 联系方式可见规则

- 仅在 `GET /api/connections/:id` 且状态 ∈ {`CONTACT_SHARED`, `CONFIRMING`, `CONFIRMED`} 时，对**双方本人**返回对方的 `ContactInfo`（按 `show_*` 过滤）；
- 进入 `CONFIRMED` 后保持可见（已是室友）；请求关闭（拒绝/取消/过期）后**再次隐藏**；
- 列表接口、匹配详情、寝室详情、通知 payload 均不出现联系方式；
- 管理员在 Admin 可见（用于纠纷处理），查看行为写审计。

### 2.6 前端路由与守卫

| 场景 | 行为 |
| --- | --- |
| 无 access 且静默 refresh 失败 | 跳 `/login` |
| 已登录但画像未完成 | `/app` 工作台提示 + 强制去 `/app/onboarding/*`；匹配/寝室/请求接口返回 `PROFILE_INCOMPLETE` |
| 已有 ACTIVE 寝室 | 访问 `/app/match`、`/app/rooms` 跳 `/app/rooms/mine`（仍可看 `/app/profile`、`/app/settings`、`/app/inbox`） |
| 窗口关闭 | 页面正常打开但顶部只读横幅；发起/同意/确认/创建/管理按钮禁用；接口 409 `WINDOW_CLOSED` |
| 未登录访问 `/room/:code` | 展示公开摘要 + "登录后查看/申请" |
| 未登录访问其他 `/app/*` | 跳 `/login?next=...` |

### 2.7 通知与轮询

- 站内通知表 + 未读数接口；前端每 20–30s 轮询（页面隐藏时暂停；操作成功后立即刷新）；
- 通知写入与状态变更在同一事务；
- 不做 WebSocket/推送；
- 通知类型、payload 结构见 §3.8 和 `docs/03-数据字典与问卷.md`（v1 已批准并冻结，2026-11-15）。

## 3. 状态机（v2 定稿摘要）

> 本节定义**开发必须遵守**的转移与守卫；完整转移表、通知文案、测试用例逐步展开见 `docs/02-组寝状态机.md`（v1 已批准并冻结，2026-11-15）。冲突时以本手册 + 02 文档已批准版为准。

### 3.1 ConnectionRequest

**状态**：`PENDING`、`CONTACT_SHARED`、`CONFIRMING`、`CONFIRMED`、`DECLINED`、`CANCELLED`、`EXPIRED`

| 当前状态 | 动作 | 操作者 | 守卫 | 目标状态 | 副作用 |
| --- | --- | --- | --- | --- | --- |
| — | 创建 `INVITE` / `APPLY` | 发起人 | §2.4 共同守卫 | `PENDING` | `expires_at=+48h`；通知目标 |
| `PENDING` | 同意（第一步） | 目标 | 窗口开放、未过期、未被拉黑 | `CONTACT_SHARED` | `contact_shared_at=now`；`expires_at=+7d`；通知发起人；双方联系方式解锁 |
| `PENDING` | 拒绝 | 目标 | — | `DECLINED` | `close_reason=DECLINED`；通知发起人 |
| `PENDING` | 撤回 | 发起人 | — | `CANCELLED` | `close_reason=INITIATOR_CANCEL`；通知目标 |
| `PENDING` | 超时 | cron | `expires_at <= now` | `EXPIRED` | `close_reason=TIMEOUT`；通知双方 |
| `CONTACT_SHARED` | 确认组寝（第二步-1） | 任一方 | 窗口开放、未过期 | `CONFIRMING` | 写本人 `*_confirm_at`；`expires_at=+48h`；通知对方 |
| `CONTACT_SHARED` | 结束了解 / 撤回 | 任一方 | — | `CANCELLED` | `close_reason=END_UNDERSTANDING`（或 `INITIATOR_CANCEL`）；通知对方 |
| `CONTACT_SHARED` | 超时 | cron | `expires_at <= now` | `EXPIRED` | `close_reason=TIMEOUT`；通知双方 |
| `CONFIRMING` | 确认组寝（第二步-2） | **尚未确认的一方** | 窗口开放、未过期、本人未确认过 | `CONFIRMED` | 事务：入寝/建寝；写本人确认时间；自动取消其余在途；通知双方 |
| `CONFIRMING` | 结束了解 / 撤回 | 任一方 | — | `CANCELLED` | `close_reason=END_UNDERSTANDING` / `INITIATOR_CANCEL`；通知对方 |
| `CONFIRMING` | 超时 | cron | `expires_at <= now` | `EXPIRED` | `close_reason=TIMEOUT`；通知双方 |
| `CONFIRMED` / 终态 | — | — | 不可再变 | — | 审计只读 |

**额外规则**：

- 同一方重复确认 → `409 ALREADY_CONFIRMED`；
- 非参与者操作 → `403 NOT_PARTICIPANT`；
- 已关闭请求操作 → `409 INVALID_STATE`；
- 管理员可从任意在途状态强制关闭 → `CANCELLED`，`close_reason=ADMIN`，写审计并通知双方；
- 确认超时：第一次确认后 48h 内另一方未确认 → `EXPIRED`。

### 3.2 Room

**状态**：`RECRUITING`、`FULL`、`LOCKED`、`ARCHIVED`、`DISSOLVED`

| 当前状态 | 动作 | 操作者 | 守卫 | 目标状态 | 副作用 |
| --- | --- | --- | --- | --- | --- |
| — | 创建寝室 | 无 ACTIVE 寝室的学生 | 画像完整、窗口开放、容量 ∈ {2,4,6}、同院同性别 | `RECRUITING` | `member_count=1`；创建 OWNER 成员；生成 9 位 code |
| `RECRUITING` | 组寝确认（入寝） | 请求双方 | 有空位、窗口开放、同院同性别、目标无寝室 | `FULL`（满员）/ `RECRUITING` | `member_count+1`；写成员；通知成员 |
| `RECRUITING` | 锁定 | 房主 | — | `LOCKED` | 关闭该寝室全部在途请求（`LOCKED`）；通知相关方 |
| `LOCKED` | 解锁 | 房主 | — | `RECRUITING` | 写审计；通知可选 |
| `RECRUITING` / `FULL` / `LOCKED` | 解散 | 房主 | — | `DISSOLVED` | 成员全部 `LEFT`（`DISSOLVED`）；关闭在途请求；取消转让；通知成员 |
| `RECRUITING` / `FULL` / `LOCKED` | 成员退出 | 非房主成员 | — | `FULL` → `RECRUITING`；其余保持 | `member_count-1`；`left_at`；通知房主 |
| `RECRUITING` / `FULL` / `LOCKED` | 移除成员 | 房主 | 目标为 ACTIVE 成员且非房主 | `FULL` → `RECRUITING`；其余保持 | 目标 `REMOVED`；`member_count-1`；通知双方 |
| 任意在途状态 | 超时归档 | cron | `TimeWindow.end_at <= now` | `ARCHIVED` | 在途请求 `EXPIRED`；转让取消；成员关系转 `ARCHIVED` 只读（不占用一人一寝）；通知成员 |
| 任意在途状态 | 管理员强制解散 | 管理员 | — | `DISSOLVED` | 同解散；审计 |

**规则**：

- **房主不可退出**：只能先转让或解散；`POST /api/rooms/:id/leave` 房主调用返回 `409 OWNER_MUST_TRANSFER_OR_DISSOLVE`；
- **容量不可变**：创建后不能修改容量/扩员；满员后只能换寝（退出/解散/转让）；
- **状态一致性**：`RECRUITING` 必有空位（`member_count < capacity`）；`FULL` 必满员；`LOCKED`/`ARCHIVED`/`DISSOLVED` 不参与广场；
- **锁定的在途请求**：全部关闭并通知；房主想保留的候选人应在锁定前完成确认；
- **归档只读**：成员关系保留为 `ARCHIVED`，可在“我的寝室”看到最终名单，但不能退出/移除/转让/解散；成员不再占用一人一寝，可在新窗口重新组寝；
- **解散释放成员**：成员可立即重新创建/加入寝室（窗口开放时）。

### 3.3 RoomMember

| 当前 | 动作 | 操作者 | 目标 | 副作用 |
| --- | --- | --- | --- | --- |
| `ACTIVE` | 退出 | 本人（非房主） | `LEFT` | `left_at=now`；`reason=LEFT`；`member_count-1`；房间状态回退 |
| `ACTIVE` | 移除 | 房主 | `REMOVED` | `left_at=now`；`reason=REMOVED`；`member_count-1`；通知 |
| `ACTIVE` | 解散/禁用 | 系统 | `LEFT` | `reason=DISSOLVED` / `USER_DISABLED` |
| `ACTIVE` | 归档 | 系统 | `ARCHIVED` | `reason=ARCHIVED`；只读历史；不占用一人一寝 |
| `LEFT` / `REMOVED` / `ARCHIVED` | — | — | 不可回流 | 历史保留 |

### 3.4 RoomTransfer

| 当前 | 动作 | 操作者 | 目标 | 副作用 |
| --- | --- | --- | --- | --- |
| — | 发起转让 | 房主 | `PENDING` | 目标必须是 ACTIVE 成员；`expires_at=+24h`；通知目标 |
| `PENDING` | 接受 | 目标成员 | `ACCEPTED` | 原房主 → `MEMBER`；目标 → `OWNER`；`Room.owner` 更新；通知双方；审计 |
| `PENDING` | 拒绝 | 目标成员 | `DECLINED` | 通知房主 |
| `PENDING` | 取消 | 房主 | `CANCELLED` | 通知目标 |
| `PENDING` | 超时 | cron | `EXPIRED` | 通知双方 |
| `PENDING` | 房间解散/归档 | 系统 | `CANCELLED` | 通知双方 |

### 3.5 TimeWindow

- 按学院一条记录：`college`（唯一）、`start_at`、`end_at`、`note`；
- **未配置 = 关闭**；`start_at <= now < end_at` = 开放；
- 关闭时：登录、资料、问卷、查看页面、公开分享页可用；**创建寝室、发起/同意/拒绝/确认请求、锁定/解锁、退出/移除/解散/转让全部禁止**（`409 WINDOW_CLOSED`）；
- 每 10 分钟 cron 扫描结束窗口：在途请求 `EXPIRED`、寝室 `ARCHIVED`、转让取消、通知；
- 管理员修改窗口（延长/提前）需写审计；时间统一 `timezone.now()`，存储 UTC。

### 3.6 CONFIRMED 事务（权威伪代码）

```python
@transaction.atomic
def confirm_connection(req_id: int, user) -> ConnectionRequest:
    req = (ConnectionRequest.objects
           .select_for_update()
           .select_related("initiator", "target", "room")
           .get(pk=req_id))

    if user.id not in (req.initiator_id, req.target_id):
        raise PermissionDenied("NOT_PARTICIPANT")
    if req.status == req.Status.CONFIRMING:
        if user.id == req.initiator_id and req.initiator_confirm_at:
            raise Conflict("ALREADY_CONFIRMED")
        if user.id == req.target_id and req.target_confirm_at:
            raise Conflict("ALREADY_CONFIRMED")
    if req.status not in (req.Status.CONTACT_SHARED, req.Status.CONFIRMING):
        raise Conflict("INVALID_STATE")

    now = timezone.now()
    if req.status == req.Status.CONTACT_SHARED:
        if user.id == req.initiator_id:
            req.initiator_confirm_at = now
        else:
            req.target_confirm_at = now
        req.status = req.Status.CONFIRMING
        req.expires_at = now + timedelta(hours=48)
        req.save()
        notify_counterpart(req, "CONFIRM_PENDING")
        return req

    # 第二步：补齐本人确认时间
    if user.id == req.initiator_id:
        req.initiator_confirm_at = now
    else:
        req.target_confirm_at = now

    if not (req.initiator_confirm_at and req.target_confirm_at):
        req.save()
        return req

    # 双方都已确认：事务内落寝
    if req.room_id:
        room = Room.objects.select_for_update().get(pk=req.room_id)
        if room.status != Room.Status.RECRUITING or room.member_count >= room.capacity:
            raise Conflict("ROOM_FULL")
        joiner = req.target if req.type == req.Type.INVITE else req.initiator
        RoomMember.objects.create(room=room, user=joiner,
                                  role=RoomMember.Role.MEMBER,
                                  status=RoomMember.Status.ACTIVE)
        room.member_count += 1
        room.status = (Room.Status.FULL if room.member_count >= room.capacity
                       else Room.Status.RECRUITING)
        room.save()
    else:
        # 人-人邀请：建寝，发起人为房主
        room = Room.objects.create(
            code=generate_room_code(), owner=req.initiator,
            capacity=req.capacity_pref or 4, member_count=2,
            college=req.initiator.college, major=req.initiator.major,
            gender=req.initiator.gender,
            status=(Room.Status.FULL if (req.capacity_pref or 4) == 2
                    else Room.Status.RECRUITING),
        )
        RoomMember.objects.create(room=room, user=req.initiator,
                                  role=RoomMember.Role.OWNER, status=RoomMember.Status.ACTIVE)
        RoomMember.objects.create(room=room, user=req.target,
                                  role=RoomMember.Role.MEMBER, status=RoomMember.Status.ACTIVE)

    req.status = req.Status.CONFIRMED
    req.save()
    cancel_other_open_requests(req)   # close_reason=AUTO_CANCELLED + 通知
    notify_both(req, "CONFIRMED")
    audit(req, "CONNECTION_CONFIRMED")
    return req
```

**必须注意**：

- 事务失败（满员/锁定/解散/归档/性别/窗口/一人一寝）整体回滚，**不写任何半成品**；
- 捕获数据库唯一约束冲突（`IntegrityError`）→ 映射 `409 ALREADY_IN_ROOM` / `DUPLICATE_REQUEST`；
- 建寝/入寝后校验 `member_count` 与 `RoomMember` 的 ACTIVE 数量一致；
- 事务内写 `Notification` + `AuditLog`（与状态变更同生共死）。

### 3.7 关闭原因（`close_reason`）

`DECLINED`、`INITIATOR_CANCEL`、`END_UNDERSTANDING`、`TIMEOUT`、`FULL`、`LOCKED`、`ROOM_DISSOLVED`、`ARCHIVED`、`USER_DISABLED`、`RATE_LIMITED`、`ADMIN`、`BLOCKED`（拉黑）、**`AUTO_CANCELLED`（v2 新增：组寝成立自动取消其余请求）**。

### 3.8 通知矩阵（v2）

| 事件 | 接收者 | `Notification.type` | `payload` 关键字段 |
| --- | --- | --- | --- |
| 收到邀请/申请 | 目标 | `CONNECTION_RECEIVED` | `connection_id`、`from_nickname`、`room_code?` |
| 对方同意（第一步） | 发起人 | `CONTACT_SHARED` | `connection_id` |
| 对方确认（第二步） | 尚未确认方 | `CONFIRM_PENDING` | `connection_id` |
| 组寝成立 | 双方 | `CONFIRMED` | `connection_id`、`room_code` |
| 被拒绝 | 发起人 | `DECLINED` | `connection_id` |
| 请求过期/取消 | 另一方 | `SYSTEM`（或对应类型） | `connection_id`、`reason` |
| 新成员加入 | 寝室成员 | `MEMBER_JOINED` | `room_code`、`nickname` |
| 成员退出/被移除 | 房主/成员 | `MEMBER_LEFT` | `room_code`、`nickname` |
| 房间满员/锁定/解散 | 相关成员 | `ROOM_FULL` / `ROOM_LOCKED` / `ROOM_DISSOLVED` | `room_code` |
| 转让发起/接受/拒绝/过期/取消 | 对应方 | `TRANSFER_RECEIVED` / `TRANSFER_ACCEPTED` / `TRANSFER_DECLINED` / `TRANSFER_EXPIRED` / `TRANSFER_CANCELLED`（v2 新增） | `room_code`、`transfer_id` |
| 窗口即将关闭/已归档 | 相关用户 | `WINDOW_CLOSING` / `ROOM_ARCHIVED`（v2 新增） | `college`、`end_at` 或 `room_code` |
| 举报处理结果 | 举报人 | `SYSTEM`（可选） | `report_id`、`status` |

### 3.9 并发与一致性不变量

1. 一人同时最多一个 `ACTIVE` `RoomMember`（部分唯一索引）；
2. 一个寝室同时最多一个 `ACTIVE` `OWNER`（部分唯一索引）；
3. 同一对用户双向最多一个在途请求（`(initiator,target)` 部分唯一 + service 反向检查）；
4. 同一人同一寝室最多一个在途 `APPLY`（部分唯一）；
5. 同一寝室对同一目标最多一个在途 `INVITE`（部分唯一）；
6. `Room.member_count == ACTIVE` 成员数（事务内维护，接口不直接 `count()`）；
7. `RECRUITING` ⇒ 有空位；`FULL` ⇒ 满员；
8. 抢最后空位/双方同时确认必须走行锁事务，禁止先查后写；
9. 锁顺序：`TimeWindow → Users(id 升序) → ConnectionRequests(id 升序) → Room → RoomTransfer → RoomMembers`；请求行必须先于 `Room`，避免与 confirm 路径成环。

### 4.5 并发写法（必须遵守）

1. 所有状态变更入口：`transaction.atomic` + `select_for_update` 锁定请求行/房间行/转让行；
2. 抢最后空位：锁 `Room` 行后重新校验 `status/member_count`；
3. 双方同时确认：锁 `ConnectionRequest` 行，按 §3.6 补齐时间戳；
4. 唯一约束作为最后保险：捕获 `IntegrityError` → 映射业务错误码；
5. 禁止在事务外"先查再改"；
6. 禁止用 `members.count()` 代替 `member_count`（服务层维护冗余字段）。

## 5. 问卷 v1 与匹配算法 v1

> 本节是 **v1 基线**（2026-11-15 确认"先按 A 做，后期更好的想法再变更"）。完整题库、选项映射、文案见 `docs/03-数据字典与问卷.md`（v1 已批准并冻结，2026-11-15）；本节锁定结构、维度、公式与口径。

### 5.1 六维定义

| 维度 key | 名称 | 含义 | 主要来源 | 默认权重 |
| --- | --- | --- | --- | --- |
| `sleep` | 作息规律 | 入睡/起床时间、熬夜频率、早起需求 | 硬指标 + 软指标 | 20 |
| `clean` | 整洁习惯 | 打扫频率、物品归位、公共区容忍度 | 硬指标 + 软指标 | 20 |
| `social` | 社交活跃 | 带朋友回寝、聚餐/活动频率、独处需求 | 软指标 | 15 |
| `noise` | 安静需求 | 对声音/外放/电话的敏感度 | 硬指标 + 软指标 | 15 |
| `boundary` | 边界感 | 访客、借用物品、隐私、作息打扰容忍 | 硬指标 + 软指标 | 15 |
| `spend` | 消费习惯 | 空调/水电/公共用品分摊偏好 | 软指标 | 15 |

> 权重合计 100，可在算法常量中调整（改权重需在决策记录登记）。

### 5.2 问卷结构（`Profile` JSON）

```json
{
  "hard_answers": {"smoke": "no", "sleep_time": "23:00", "snore": "no", "pet": "ok", "visitor": "rarely"},
  "soft_answers": {"clean": 5, "social": 2, "noise": 4, "boundary": 4, "spend": 3, "sleep_regular": 4},
  "red_lines": ["smoke", "late_return"],
  "red_lines_confirmed": true,
  "tags": ["早睡", "猫派", "自习搭子"],
  "prompts": {
    "weekend": "周末我更愿意在图书馆待一天，晚上回来打两把游戏。",
    "vibe": "希望寝室是能互相借充电线、也能各戴耳机的关系。"
  }
}
```

要求：

- 硬指标：单选/多选，全部必答；用于红线冲突判定与维度换算；
- 软指标：1–5 分，全部必答；
- 红线：从固定清单多选（可空，但需显式确认"无红线"）；
- 词条：从固定词库选 3–8 个；
- prompts：从题库选 2–3 个问题作答，单条 ≤ 120 字；至少 2 条才算完整；
- 问卷版本 `questionnaire_version="v1"`；字段只增不改，新增给默认值并写数据字典。

### 5.3 完整度公式

| 项 | 分值 | 规则 |
| --- | --- | --- |
| 基本资料 | 20 | 昵称/性别/年级/学院/专业齐全 |
| 硬指标 | 20 | 全部作答 |
| 软指标 | 30 | 全部 6 项作答 |
| 红线 | 10 | 选择红线或显式“无红线”（`red_lines_confirmed=true`） |
| 标签 | 10 | ≥3 个 |
| prompts | 10 | ≥2 条且每条 ≤120 字 |

- `completeness = 各项之和`（0–100）；
- **匹配/请求门槛：completeness = 100**（未完成只可查看自己的画像）；
- 后端在 `Profile` 提交时计算并落库；前端展示分步进度。

### 5.4 匹配候选池（硬过滤）

候选必须同时满足：

1. `status=ACTIVE`；
2. `college == 当前用户学院`；
3. `gender == 当前用户性别`；
4. `Profile.completeness == 100`；
5. 没有 `ACTIVE` `RoomMember`；
6. 不是自己；
7. 双向无 `Block`；
8. 未被管理员禁用。

排序：`match_score DESC` → `completeness DESC` → `last_active/updated_at DESC`；分页 20/页。

### 5.5 契合度公式（v1）

```text
dim_score(a, b) = 100 - |a.dims[d] - b.dims[d]|          # 0–100
base = Σ(weight[d] * dim_score(a,b)[d]) / 100            # 0–100
tag_bonus = min(6, 2 * |a.tags ∩ b.tags|)                # 0–6
red_penalty = min(30, 15 * red_conflict_count)           # 0–30
score = clamp(base + tag_bonus - red_penalty, 0, 100)
if red_conflict_count > 0: score = min(score, 59)         # 红线冲突封顶
```

- **红线冲突**：一方的 `red_lines` 命中另一方的硬指标（如 A 的红线含 `smoke`，B 的 `hard_answers.smoke=yes`），计 1 次冲突；
- 冲突不硬性排除：列表可见、降分、详情琥珀色提示；发起请求时二次确认弹窗；
- 相同词条额外加权（最多 +6），不改变红线封顶；
- prompt 不参与打分，只用于展示；
- `POST /api/match/:uid/score` 返回同一套分数 + 理由 + 冲突列表。

### 5.6 推荐理由（3 条）

规则：取加权贡献最高的 2 个维度 + 1 条公共标签（没有则取第 3 维度），生成中文模板：

- `“你们都把「早睡早起」看得很重，作息分接近。”`
- `“整洁习惯高度一致，公共区摩擦会少很多。”`
- `“都有「猫派」标签，容易聊到一起。”`
- 若存在红线冲突：追加琥珀色提示 `“注意：对方有吸烟习惯，与你的红线冲突。”`（理由条数仍 3 条，冲突单独字段返回）。

### 5.7 红线清单（v1 初稿）

`smoke`（吸烟）、`snore`（打鼾）、`late_return`（凌晨归寝）、`pet`（宠物）、`alcohol`（饮酒）、`game_noise`（游戏外放）、`visitor_freq`（频繁访客）、`ac_dc`（空调温度冲突）、`clean_low`（卫生容忍低）。

> 完整题干、选项、维度映射、软指标题面在 `docs/03-数据字典与问卷.md`。

### 5.8 prompt 题库（v1 初稿，选 2–3 条）

1. 「周末我更愿意……」
2. 「关于我的一件小事：……」
3. 「理想的寝室氛围是……」
4. 「我最不能接受室友……」
5. 「如果室友带朋友回来，我希望……」
6. 「用一句话介绍我的作息：……」

展示规则：匹配列表用第一条 prompt 回答作大标题；详情页用全部 prompt Q&A；无 prompt 时回退到昵称 + 标签。

### 5.9 计算示例

A：`sleep=90, clean=80, social=40, noise=70, boundary=80, spend=50`；B：`sleep=85, clean=85, social=35, noise=65, boundary=75, spend=55`；无红线冲突、共享 1 个标签。

```text
base = (20*95 + 20*95 + 15*95 + 15*95 + 15*95 + 15*95) / 100 = 95
tag_bonus = 2
score = 97
```

### 5.10 冻结与变更

- v1 自评审通过起冻结；后续调整（维度/权重/红线/prompt）必须：改本手册与数据字典 → 记决策记录 → 旧数据兼容（JSON 只增不改）。
- `questionnaire_version` 用于区分历史画像；匹配时同版本优先，跨版本仍可算分并提示。

### 6.7 响应式、动效与可访问性

## 7. API 契约（v2）

### 7.1 通用约定

- 前缀 `/api/`；JSON；时间 ISO 8601 UTC（`2026-11-15T08:00:00Z`），前端按本地时区展示；
- 学生接口认证：`Authorization: Bearer <access>`（access 只存内存）；
- 刷新/登出走 HttpOnly Cookie（`/api/auth/`），见 §8.3；
- 列表分页：`{count, next, previous, results}`，默认 20/页，`page`、`page_size`（≤50）；
- 统一错误：`{"code": "...", "message": "...", "detail": {...}}`；字段校验错误放 `detail.fields`；
- 幂等：重复动作返回 409（不重复扣减/写通知）；创建类接口同参数重复提交由唯一约束兜底；
- OpenAPI：`drf-spectacular` 生成；`GET /api/schema/`（DEBUG 或 staff）、`/api/docs/`（DEBUG）；提交 `docs/openapi.yaml` 作为前后端契约。

## 8. 架构与运行逻辑

### 8.1 组件

```text
浏览器（Vue 3 SPA）
  ├─ Pinia（access、me、未读数、筛选）

  └─ 路由守卫（登录/画像/寝室/窗口）

        ▼
Nginx（生产） 或 Vite dev server（开发）
  ├─ /              → frontend/dist 或 Vite
  ├─ /api/*         → Gunicorn / Django runserver
  ├─ /admin/*       → Django Admin
  └─ /static/*      → collectstatic
        ▼
Django 5.2 + DRF
  ├─ DRF API（accounts/profiles/matching/rooms/connections/notifications/adminops）
  ├─ Service 层（状态机/权限/窗口/事务/行锁/通知/审计）
  ├─ Django Admin（Jazzmin，管理端）
  └─ cron 管理命令（过期/归档/提醒）
        ▼

```

### 8.2 一次写操作的链路（以"确认组寝"为例）

```text
Vue 按钮
  → axios POST /api/connections/:id/confirm （Bearer access）
  → 路由/视图：JWTAuthentication → IsAuthenticated
  → Service.confirm_connection（transaction.atomic）
      1. SELECT ... FOR UPDATE 锁请求行
      2. 校验参与者/状态/窗口/时间戳
      3. 锁房间行；校验状态/空位/性别/学院/一人一寝
      4. 写 RoomMember / Room.member_count / Room.status（或建寝）
      5. 请求置 CONFIRMED；写 Notification（双方）
      6. 关闭双方其余在途请求 + 通知
      7. 写 AuditLog
  → 200 + 新状态（含 room_code / actions）
  → 前端刷新详情、未读数；对方轮询到通知
```

### 8.3 认证与 Cookie（前后端必须一致）

| 项 | 规则 |
| --- | --- |
| access | 30 分钟；**只存 Pinia 内存**，不写 localStorage/sessionStorage |
| refresh | 7 天；`HttpOnly; Secure(生产); SameSite=Lax; Path=/api/auth/; Max-Age=604800` |
| 登录 | body 返回 `access`；`Set-Cookie: refresh=...` |
| 刷新 | `POST /api/auth/refresh` 浏览器自动带 Cookie；轮换 refresh（`ROTATE_REFRESH_TOKENS=True`）并更新 Cookie；旧 refresh 入黑名单 |
| 401 | Axios 拦截器单航班刷新（同一时刻只发一个 refresh，其余排队），成功后重放一次原请求；失败清空内存 + 跳登录 |
| 启动 | 页面刷新先静默 refresh 恢复会话；失败再判未登录 |
| CSRF/来源 | refresh/logout 校验 `Origin/Referer` 属于 `ALLOWED_ORIGINS`；SameSite=Lax；Django Admin 继续走 CSRF |
| 开发 | `REFRESH_COOKIE_SECURE=false`（http://localhost）；生产 true |
| 同源 | 开发：Vite proxy `/api`、`/admin`、`/static` 到 8000；生产：Nginx 同域；**不启 CORS** |
| 注销 | 清 Cookie + refresh 黑名单 + 前端清空内存/轮询 |
| Admin | Django Session；学生 token 不能进 Admin；`is_staff=1` 才可登录 |
| 注意 | 浏览器地址统一用 `http://localhost:5173`（不要 localhost 与 127.0.0.1 混用，Cookie 不共享） |

### 8.6 安全控制

- 密码：Django 校验器（长度/常见密码/相似性）；不记录明文；重置功能本期不做（管理员可后台改）。
- 登录/验证码/搜索/请求/举报全限频（§7.5）。
- 邮箱枚举：`send-code` 统一 204；错误提示不区分"邮箱不存在"。
- 邀请码：8–12 位随机、可停用、可限次/过期；注册失败提示统一 `INVITE_INVALID`；暴力尝试限频。
- 对象级权限全部在 service；serializer 显式字段，禁止 `__all__`。
- 输入：DRF serializer 校验 + ORM 参数化；富文本不接收（纯文本）；XSS 由 Vue 转义 + 后端不返回 HTML。
- CSRF：Cookie 刷新端点 Origin 校验 + SameSite；Admin 用 Django CSRF。
- 传输：生产 HTTPS/HSTS；开发 http 仅本机。
- 日志脱敏：token/密码/联系方式不入日志；审计 meta 不含联系方式原文。
- 管理员操作全部写 `AuditLog`；`is_staff` 最小授权。
- 依赖：锁版本 + 定期 `pip-audit`/`npm audit`（P1 负责，发现高危升级）。

### 8.7 性能与缓存

- 画像 `dims` 提交时计算落库，匹配时只读；列表分页 + 每页 20；同学院候选量级 ≤ 数百；
- 查询用 `select_related`/`prefetch_related`；禁止 N+1；`Room.member_count` 冗余避免 count；
- 索引：§4.4；匹配候选过滤依赖 `User(college, gender, status)` 复合索引（v2 新增）；
- 通知轮询只查 unread count（索引 `user, read_at`）；
- 前端：ECharts 按需引入（`echarts/core` + RadarChart）；字体 woff2 子集；图片 WebP；路由懒加载；
- 缓存：不做业务缓存；限频用 Django DB cache；生产如需 Redis 再单独立项。

### 8.8 日志与审计

- 应用日志：结构化（时间/级别/request_id/user_id/路径/耗时/状态码）；错误含 traceback（仅服务端）；

### 9.5 常见问题

| 现象 | 原因/处理 |
| --- | --- |
| `python` 打开微软商店 | 系统 Python 是占位；用 `.\.venv\Scripts\Activate.ps1` 或 `uv run` |
| `Activate.ps1` 被禁止 | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
| 端口占用 | 5433/8000/5173 被占；用 `netstat -ano` 查占用，必要时换端口并同步 `.env`/Vite proxy |
| Cookie 不生效 | 地址混用 localhost/127.0.0.1；`Secure` 在 http 下被浏览器拒（开发置 false）；Path 必须 `/api/auth/` |
| 刷新死循环 | 401 拦截器需排除 `/api/auth/refresh`；单航班锁 |
| PG 启动失败 | 数据目录被占用/残留 `postmaster.pid`；看 `server.log`；关闭后重启 |
| psql 不在 PATH | 用绝对路径 `D:\tools\pgsql16\bin\...` 或临时加入 PATH |
| 中文乱码 | 终端 `chcp 65001`；Python 源文件 UTF-8；`PYTHONUTF8=1` |
| 迁移冲突 | 只由 P1 合并迁移；冲突时删除本地未应用迁移重新生成（禁止手改已应用迁移） |
| 前端跨域/Cookie | 用 Vite proxy，不要直连 8000；不要启 CORS |

### 10.3 命名与规范

- Vue 组件 PascalCase；composable `useXxx`；store `useXxxStore`；类型 PascalCase；常量 UPPER_SNAKE；
- 前端页面私有组件放同目录；全站复用放 `components/common`；
- Python：ruff（line-length 100）；Vue/TS：ESLint + Prettier（单引号、无分号？以 `.prettierrc` 为准，P3 初始化时定并写 README）；

| 状态机 bug | 最致命（脏数据/重复入寝） | 状态机集中 service；行锁 + 唯一约束；18+ 用例；Lead 评审 |
| 性别规则引入的边界 | 匹配/入寝不一致 | 性别注册后不可改；`Room.gender` 快照；跨性别统一 404/403；专项测试 |
| 时间窗语义复杂 | 误拦截/漏拦截 | 未配置=关闭；service 统一守卫；cron 幂等；测试 WIN-01/02 |
| Agent 并行写冲突 | 覆盖/返工 | 独占写权限；共享文件 owner；迁移单点；契约先行；每日同步 |
| 无用户照片导致页面空 | 视觉效果下降 | 默认头像 + prompt + 雷达画像卡；首页用实拍素材 |
| 素材版权 | 下架/纠纷 | 只用免费图库/自绘；登记来源与许可；不用 Hinge 素材 |
| 功能蔓延（答辩/部署/聊天） | 15 天不够 | 本手册范围冻结；砍功能顺序；部署/答辩后置 |
| 限频误伤演示 | 演示失败 | 开发环境可调常量；种子账号预热；演示脚本避开限频路径 |
| 数据字典/题库变更 | 画像不兼容 | JSON 只增不改；`questionnaire_version`；决策记录 |
| 联系方式泄漏 | 隐私事故 | 序列化显式字段；专项测试；代码审查；日志脱敏 |
